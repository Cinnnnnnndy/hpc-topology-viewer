| 用途 | 成不成立 |

## 2. 为什么不能当 evaluation（四条理由，任一条单独成立）

**一、归属错位。** 这 8 份报告是 B 仓库另一套工具链（msprof-analyze 的 10 个 recipe + advisor + MindStudio Insight
视图 + 一组 profiling skills）产出的，没有任何一个结论是用本仓这套并行拓扑视图看出来的。
用「工具甲找到了 bug Y」证明「框架乙的设计原则 X 有效」，中间缺的正是 evaluation 本身。

**二、覆盖率近乎为零。** A1–A8 里 A1/A2/A3/A4/A6/A7/A8 七条测的是配置校验与视觉编码，与 profiling 数据正交；
只有 A5 沾边，而且是被**别的工具**答对的。PRD 自己写的 M1 完成定义（A1、A2、A4、A6、A7 全部通过）
与这批数据的交集是**空集**。

**三、北极星指标零样本。** §11 指定误判率为核心量化证据，8 份报告里没有一个人类被试、没有一次记录在案的误判。
误判率按定义只能来自人，不可能从机器生成的报告里析出。反倒是 verl 那份显示：
专业工程师在信息不足时没有判错，他知道自己不能下结论——这对「不用我的工具就会判反」这个隐含假设是不利证据。

**四、内部效度已被数据本身击穿。** 见 §0.5 的 pangu2.0flash 数据完整性问题。

## 3. 逐条证据映射（能用的部分，写进论文时这样引）

### P4 · 只呈现单卡时间线丢掉跨 rank 关系、把「等待」误判为「链路慢」，归因方向完全反了　✅ 直接支持
**证据**：level2_profiling_analysis_20260610 §3.2 + ascend_analysis_20260526 §3.1（同一数据集）：rank0 的单卡 trace 上看到的是 hcom_batchSendRecv__128_4_1 elapse 158.55 ms，只看这一条会读成「P2P 链路慢」；而 transit 只有 0.40 ms、wait 158.10 ms（99.7%），真正的原因在**另一张卡**——rank2 此时在算 vocab=151936 的 Exp/Sub/RealDiv/Cast 链（末级独有 ~160 ms）。HcclPerRankStats 把这件事钉死：同一个 batchSendRecv 在 rank0/1 是 313.9 / 323.0 ms，在 rank2/3 只有 72.7 / 75.0 ms。

**局限**：这是 P4 描述的现象在真实数据里成立的证明，但**不是本框架修正了它**——修正它的是 msprof-analyze 的 ClusterTimeSummary / HcclPerRankStats 这套集群级表格。报告拿到正确归因用的是表，不是任何一张跨 rank 时间线图。

### P4 · 单卡视角在方法上不足以归因（更强的一手证词）　✅ 直接支持
**证据**：ascend_analysis_verl_20260602 §3.6 与第 4 章：只有 rank0 的数据，AllReduce wait 高达 9.4 s，报告作者**明确拒绝下结论**——「高 wait 既可能是通信暴露/串行，也可能是其他卡为 straggler 致 rank0 早到空等；区分二者必须补采 ≥1–2 张其他卡」。

**局限**：这是全批里最好的一条材料：它不是「工具画错了」，而是一位工程师在真实工作中因为缺少跨 rank 相对关系而**被迫停在半路**。但它同时也说明——专业工程师并没有被误导，他知道自己不能下结论。所以它支持的是 P4 的前半句（信息不足），支持不了后半句（用户会判反）。「会判反」这个假设在这批数据里一个实例都没有。

### A5 · 通信耗时不均时，工具提示应指向耗时【短】的 rank（FR-8 归因提示 / §12「等待长的是受害者，等待短的是嫌疑人」）　✅ 直接支持
**证据**：三份数据同构地给出了「短等待 = 嫌疑人」的实例：(a) level2_20260610：wait 短的 rank2/3（175.8/159.7 ms）计算 400 ms，是元凶；wait 长的 rank0/1（318.3/339.9 ms）是受害者。(b) profile_dir_20260618：stage3 rank6/7 stage 等待仅 392.3/848.3 ms、计算 9454/9060 ms，其余 6 卡等 3.51–4.05 s。(c) ascend_analysis_20260526 §3.1 同例。

**局限**：两点必须说破。一、这些报告**已经**正确归因了，所以它们证明的是「这条判据是对的」，而不是「不用本框架就会判错」——后者才是 A5 的价值主张，这批数据零证据。二、A5 只覆盖「通信等待」一种空闲；MultiProf 的 rank15 是另一种（device free 40.7% 是 host 饿死，不是等别人），naive 套用 A5 会得出「free 长 = 受害者」的错误结论，而它恰恰是 slowAffectCount=70 的头号阻塞源。这说明 FR-8 的单条启发式在真实场景里**不充分**，需要先区分 free（host-bound）与 communication wait（peer-bound）。这一条如实写进论文比硬撑 A5 更有价值。

### FR-7 · V2 多 rank 时间线：多 rank 时间轴叠在同一坐标上，标出通信算子的进入/退出时刻，「必须能看出谁在等谁」　✅ 直接支持
**证据**：MultiProfLevel2MemoryUB §3.3：Rank 15 computing 52.2% / free 40.7%（2.57 s），slow_rank 表 slowAffectCount=70（次高 24），且各 rank 算子 Count 完全一致 → 判为「伪快卡 / Host 下发型慢卡」：NPU 饿死 → 空闲 → 最晚到 collective → 阻塞全集群。node2 平均 free 18.3% vs node1 9.1%。

**局限**：支持的是「需要跨 rank 相对关系」这个需求本身。但要注意根因（8390 次 aclopCompileAndExecute 在线编译 + 40.4% AICPU 算子）**完全落在本框架的作用域之外**——并行拓扑视图看不到在线编译，也看不到 AI_CPU 回退。也就是说：这个 incident 能证明「跨 rank 视图有用」，但用本框架看完之后，用户仍然到不了根因。

### DP-3 · 有序维优先上轴（pp_rank 大小有意义，必须占一根轴）　⚠️ 间接/需额外论证
**证据**：四份多卡报告里 PP stage index 都是唯一有序且有意义的维：profile_dir stage0→s3 计算 6325/6005/6174/9454 ms；pangu 声称 stage0–2 ~8292 ms vs stage3 ~12700 ms；level2 stage0 231 ms vs stage1 400 ms。而 dp_rank 在同一 stage 内高度对称（rank0 vs rank1 = 6325.6 vs 6359.1 ms，差 0.5%），折叠不丢信息。

**局限**：这是「DP-3 的前提在真实配置里成立」，不是「按 DP-3 画出来的图更好用」。而且样本有偏：这批数据里 TP 要么=1 要么=8，CP 全是 1，EP 只有 pangu 一份且证据不可用——「对称维可折叠」这半句几乎没有被检验。

### FR-11 · 配置诊断：气泡率估算 (PP−1)/GA、GA ≥ PP 校验　⚠️ 间接/需额外论证
**证据**：实测 bubble 率三个点：level2 39%（首级空等 313 ms / 810 ms，PP=2）、profile_dir 35%（3.77 s / 10.80 s，PP=4）、pangu 声称 26%（4.26 s / 16.20 s，PP=4）。level2 §3.4 明确用了 bubble ≈ (p−1)/(p−1+m) 这条公式并归因到 micro-batch 数偏少。

**局限**：三个点可以做一次「估算式 vs 实测」的对照，但这批 bubble 主体是**负载不均**造成的（末级 1.5×），不是 1F1B 固有气泡；(PP−1)/GA 这条公式在负载不均下本来就不适用。硬把它们对上会被审稿人一眼看出口径错配。要用只能反过来用：证明「教科书气泡公式在真实作业里预测不准，因为它假设各 stage 等负载」——那是另一篇论文的论点。

### rank-topology-3d 第十层「载体」· 通信域跨不跨物理边界决定带宽档位，且「照直觉画成 node 内快、node 间慢会画反」　⚠️ 间接/需额外论证
**证据**：MultiProfLevel2MemoryUB §3.4 + 第 4 章：节点内 HCCS/SDMA size-weighted 仅 16.35 GB/s（理论 ~30 的 54%），而跨节点 RDMA 24.0 GB/s ≈ 96% 理论 —— **跨节点实测比节点内更快**，正是那份文档警告的「画反」的实例。另有 profile_dir/pangu：跨节点 RDMA 24.2–24.3 GB/s vs 节点内 LOCAL allreduce 655–661 GB/s（两个数量级差），说明「物理边界 → 带宽档」的结构确实存在但不是单调的。

**局限**：两处错配。一、B 仓库全部是 910B + HCCS/RoCE，**没有任何一份 UB / 灵衢 / 超节点 / CloudMatrix384 的数据**，而第十层那份文档的带宽表（196 GB/s 单向、384 卡超节点）说的是另一代 fabric。二、MultiProf 那个「跨节点更快」是达成率异常（HCCS 只跑到 54%）造成的，不是拓扑本身的性质——用它论证「别按直觉画」逻辑上成立，但需要额外说明这是效率问题不是架构问题。

### G2 · 让通信可见：看清什么时候、谁跟谁、用什么原语（FR-4 三种原语三种线型）　⚠️ 间接/需额外论证
**证据**：pangu2.0flash §3.2/§3.3 给出了三种原语在同一 step 里的实测代价对照：EP all-to-all 88 次/step（dispatch ~18 ms、combine ~12 ms，合 1320 ms）、PP P2P batchSendRecv 96 次 ≈ 149 ms（单次 1.55 ms、包 37.7 MB）、DP allReduce rank0 ~1.15 s/2step。MultiProf 则给出 TP 融合原语（AllGatherMatmul / MatmulReduceScatter）把通信吞进算子内部的形态。

**局限**：两个折扣。一、pangu 这些数字目前**没有落盘证据支撑**（见 inventory），在回源核对前不可引用。二、这些数只能拿来给 L5 图层填真实标签（让示例不是玩具），它们对「三种线型必须视觉语义不同」这条主张本身不构成任何证据——那是一个感知/表达命题，只能用被试实验或表达力论证来支持。

### FR-10 · 时间轴驱动动画：MoE 层 All-to-All 成片爆发、TP 每层闪两下、DP 整步静默末尾闪一次　⚠️ 间接/需额外论证
**证据**：pangu2.0flash §3.2：44 个 MoE 层 × 2（fwd dispatch + bwd combine）= 88 次 hcom_all_to_all_v_/step —— 与「MoE 层成片爆发」的节律吻合；DP allReduce 每 step 一批、PP P2P 沿 stage 逐跳，也与文档描述的节律一致。

**局限**：同上：pangu 的落盘证据不可用。而且「节律吻合」是把并行语义的教科书结论和实测次数做了一次一致性核对，属于 sanity check，不是对动画设计有效性的评估。

### DP-5 · 宁缺毋误：画不下的东西就不画，并明确告知为什么　⚠️ 间接/需额外论证
**证据**：两处一手材料：(a) verl 报告的公开自我订正——通信子项 57%→33%，因为初版误用「逐 op 平均带宽 17.1 GB/s」而非「字节加权有效带宽 ~10 GB/s」，同一份数据不同口径差 1.7×。(b) 多份报告在证据不足时明确留空：MultiProf「显存容量未确认，memory_record 峰值仅 0.311 GB 明显不完整，故不据此判 OOM 风险」；「vocab 维未在任何算子 shape 中出现，模型名留空不猜」。

**局限**：这是「宁缺毋误在 profiling 报告写作里是好实践」的证据，跟「可视化工具应当拒绝渲染」是两件事——一个是文本口径纪律，一个是渲染决策。要接上必须自己补一步论证。不过这条材料本身很值钱：它可以直接进 methodology 章节，讲口径如何决定结论。

### G4 · 可用于诊断：从图能导向可行动的判断，能区分【利用率类】问题并定位到具体 rank　⚠️ 间接/需额外论证
**证据**：利用率一侧覆盖充分：level2/profile_dir/MultiProf 都能定位到具体 rank（rank2/3、rank6/7、rank15）并给出可执行改动（PP 非均匀切分、关 JIT、去 AICPU）。

**局限**：G4 的另一半——「区分 OOM 类问题」——**零证据**：MultiProf 的 memory_record 峰值 0.311 GB 被报告自判不完整，pangu 与 profile_dir 都 profile_memory=false，只有 level2 落了 memory_record.csv（1.4 MB）且标为「备用」，报告正文没用它下过任何结论。全批 8 份报告里没有一次 OOM 诊断。

### P1 · 把并行维度与通信原语一一绑定（把 N:M 编码成 1:1），看到 All-to-All 就以为是 MoE 而它同样可能是 Ulysses CP　❌ 零证据
**证据**：无。全批数据 CP 一律 =1（pangu 与 profile_dir 的配置行明写 CP1，其余报告根本没有 CP 维），没有任何一份出现 Ulysses 语义、没有任何一次 All-to-All 归因错误。唯一的 All-to-All 是 pangu 的 EP token dispatch/combine —— 那正是「MoE → All-to-All」这条**教科书绑定成立**的情形，恰好是 P1 想反驳的那一半的正面例子。

**局限**：必须承认：P1 是 PRD 自称的四类结构性错误之首、也是 DP-1 与 FR-5 的全部理由，而它在这批真实数据里**一个实例都没有**。不要拿 pangu 的 EP all-to-all 去凑——那会被审稿人当场反用。要支持 P1 只有两条路：找一份真实的 Ulysses CP / SP 双语义作业，或者用受控的误判率实验（见 legitimateStudyDesigns #4）。

### P2 · 把 CP 硬加成卡网格的第四根轴（混淆切分维与时间轴）· A4 卡网格 axis 取值域不含 CP · FR-9 V5 输入分布视图　❌ 零证据
**证据**：无。CP 在全部 8 份数据里都是 1 或不存在。

**局限**：无可辩解的空白。CP=1 意味着这批数据连「CP 在图上长什么样」都不产生，更不用说验证「CP 与 DP 在卡网格上分不清」。

### P3 · 把 rank 画成容器（地址被当成形状）· DP-2 地址只标不画 · A2 找不到任何代表 rank 的几何体　❌ 零证据
**证据**：无，且原则上不可能有。这是一条关于**视觉编码**的命题，profiling 数据既不能证实也不能证伪它。

**局限**：报告里 rank 一律以编号出现（rank15、rank24–31），这最多说明「工程实践中 rank 就是个编号」，与「不应画成几何体」之间隔着一整个感知实验。硬接是明显的过度延伸。

### A1（CP 三原语可选）· A3（DP 2→8 容器不变）· A6（heads=33/TP=16 报错）· A7（MoE 最小卡数 = PP × max(TP·CP, EP·ETP)）· A8（切视图保持高亮）· FR-1 配置校验　❌ 零证据
**证据**：无。这五条 + FR-1 测的是配置校验与交互状态，与 profiling 数据正交。A3 尤其无解：它要求同一模型在两个不同 DP 下的容器构成对照，而全批没有任何一次配置扫描，显存数据本身还是缺的/坏的。

**局限**：这意味着 PRD 的 M1 完成定义（A1、A2、A4、A6、A7 全通过——「它们是这个产品与现有方案的全部差别所在」）与 B 仓库数据的交集是**空集**。这批报告哪怕全部用上，也一条都碰不到 M1 的验收线。

### §11 度量 · 误判率作为北极星指标（「唯一能证明结构正确有价值的量化证据」）　❌ 零证据
**证据**：无。8 份报告里没有任何人类被试、没有任何一次记录在案的误判、没有任务完成率或归因时长。报告作者本人在需要谨慎的地方（verl 单卡）反而做出了正确的克制判断。

**局限**：这是整个嫁接方案最致命的一处：PRD 自己指定的核心量化证据，在 B 仓库里样本量为零，而且它按定义就不可能从机器产出的 profiling 报告里获得——误判率只能来自人。

## 4. 站得住的研究设计（如果要做完整 evaluation，走这些）

### 回溯性 incident 复现实验（A/B 被试，主实验，直接打北极星指标）
**工期**：8–12 周（题目与判分标准 2 周 + 预实验 1 周 + 招募与执行 3–4 周 + 分析写作 3 周）；若走 IRB/伦理审查再加 2–4 周。合规审批需与之并行启动，否则 (ii) 的 16 卡数据不能进实验材料。

**设计**：从 B 仓库选 3 个真实 incident 作为任务，标准答案取自报告并请 2 位未参与本工作的性能工程师独立复核：
(i) level2_20260610 —— 给 4 卡数据，问「谁是嫌疑人、根因是什么」。正确答案：rank2/3（wait 短、计算 400 ms）是嫌疑人，根因是末级 vocab=151936 的 lm_head + 未融合交叉熵 ~160 ms。这道题测 A5/FR-8 的归因方向。
(ii) MultiProf_20260618 —— 给 16 卡数据，问「哪张卡在阻塞集群、是不是链路慢」。正确答案：rank15（free 40.7%、slowAffectCount=70），且**不是**链路慢（HCCS 16 卡极差 <5%）。这道题测「free 型空闲 vs communication wait 型空闲」的区分能力——正是 FR-8 单条启发式覆盖不到的那一类。
(iii) verl_20260602 —— 只给 rank0 数据，问同样的问题。**正确答案是「证据不足，必须补采 1–2 张卡」**。这道题直接测 DP-5「宁缺毋误」：会不会诱导用户在信息不足时下结论。

设计：被试 24–36 人，分「训练工程师 / 性能分析师」两层配额；within-subject，拉丁方平衡任务×条件×顺序。条件 A = 原始 profiling 交付件 + MindStudio Insight 既有视图（baseline 必须由熟悉该工具的第三方配置，防止 sandbagging）；条件 B = 本框架视图。主结局：归因方向正确率（= 1 − 误判率，PRD §11 北极星）与首次正确归因时长（对应 G4 指标）。次结局：NASA-TLX、事后置信度。预注册假设、样本量与分析计划。

**能证明**：直接产出 PRD 自己指定的核心量化证据：误判率与首次正确归因时长的组间差。(iii) 单独产出一条别的可视化论文很少有的结果——「工具是否会诱导用户在证据不足时下结论」。而且因为标准答案来自另一套工具、由第三方复核，答案不是作者自定的，这一点正好把 circularity 转成方法上的优点。

**审稿人会怎么攻击**：① 被试代表性与样本量——真正懂 Megatron PP/TP 的人极难招满 30 人，审稿人会盯这一点；缓解：分层报告、报效应量与置信区间而不是只报 p 值。② baseline 被设弱（作者做条件 B、顺手削条件 A）——必须由第三方配置 baseline 并把配置公开。③ 标准答案的权威性——报告本身可能有错（pangu 那份已经证明会错），所以选题必须避开有数据完整性问题的那份，并公开复核记录。④ 学习效应与顺序效应，靠拉丁方与洗脱间隔控制。⑤ 外部效度：只在 Ascend 910B + Megatron 一种生态上做，能不能推广到 GPU/NCCL 生态会被质疑。⑥ 三个任务全部落在 P4 一类错误上——审稿人会问 P1/P2/P3 呢，必须用设计 #4 补。

### 视图充分性审计（view-sufficiency audit，无被试，最快出结果）
**工期**：2–3 周（编码手册 3 天 + 双人独立编码 5 天 + 分歧裁决 2 天 + 写作 1 周）。不依赖被试、不依赖原始数据回源，是最先能出手的一项。

**设计**：把 8 份报告的每一条结论拆成「读出它所需的最小信息元组」：需要哪个量、哪几个 rank、哪个时间区间、哪个通信域、哪一级粒度。全批约 45 个问题点（3.1–3.8 各节）。然后由两名编码者独立判定：本框架的哪个视图（V1–V5）+ 哪个图层（L1–L5）能读出它、需要几次交互到达、还是根本读不出（记 miss）。同一套编码同时施加于 baseline（MindStudio Insight 的既有视图——报告里每节都自带「问题举证视图」，是现成的对照）。产出一张 45×2 的覆盖矩阵与一份 miss 清单。

关键纪律：miss 必须如实报。预期结果里就有大片 miss——eta_eager 的 8 条预计 0 条能被并行拓扑视图读出；MultiProf 的在线编译与 AICPU 两条读不出；ascend_analysis_20260527 的单算子 pipe 利用率整份读不出。

**能证明**：两件事，都不是「更好用」而是更基础的东西：(a) 框架的**作用域边界**——它管结构性并行错误（PP 不均、通信暴露、原语落位），不管 host 下发、算子实现与单算子流水；(b) 在其作用域内的表达力覆盖率与到达成本（交互步数）。这是 expressiveness/coverage 类贡献，在可视化会议里是被接受的论证形式，而且它诚实地界定了「不做什么」，与 PRD §2.2 的非目标呼应。

**审稿人会怎么攻击**：① 编码者即作者 → 必须双人独立编码并报 Cohen's κ，最好其中一人不参与工具开发。② 「能读出」的判定阈值主观（几次交互算能读出？）→ 编码手册必须预注册并附样例。③ 覆盖率高 ≠ 更快更准 —— 审稿人会说这只证明了表达力不证明可用性；不能拿它替代设计 #1，只能作为其前置。④ 45 个问题点全部来自同一批作者、同一套 skill 流程产出的报告，问题点的分布本身有偏（比如全批没有一次 OOM 诊断），需在 threats to validity 里写明。

### 专家逐条验收 + 现有工具的 P1–P4 存在性举证（conformance study）
**工期**：3–4 周（截图取证与来源核实 1.5 周 + 专家排期与执行 1 周 + 访谈转录与编码 1 周）。第一段可与合规审批并行，因为不涉及任何实测数据。

**设计**：两段合成一项。
第一段（存在性）：不用 B 仓库数据——用现有工具（MindStudio Insight、Megatron/DeepSpeed 官方文档图、主流并行可视化项目）的公开截图与文档，逐条举证 P1–P4 四类错误**确实存在于现有方案中**：P1 找「TP→AllReduce、EP→All-to-All」的一一对应写法（A 仓库参照系 §13 勘误 K/L 自己就记录了这类写法曾出现在本文档里，可作为自证素材）；P2 找把 CP 画成卡网格第四轴的实例；P3 找把 rank 渲染成柱子/盒子的实例；P4 找只提供单卡时间线的工具。每条附来源与截图。
第二段（符合性）：请写这 8 份报告的工程师（3–5 人）+ 2–3 位无关联的第三方性能工程师，对本框架按 A1–A8 逐条做二值判定（A1/A2/A4/A6/A7/A8 是可客观判定的规范符合性项，不需要统计功效），并做半结构化访谈（每人 45 分钟）记录他们对 DP-1~5 的异议。产出一张 8 条 × 两套工具的 conformance table。

**能证明**：G3「不制造错误认知」这条主张唯一可信的证法：先证明错误在现有方案里真实存在（第一段，独立证据），再证明本框架逐条不犯（第二段，可客观判定）。同时补上了 P1/P2/P3 在 B 仓库数据里完全缺失的空白——它们的存在性不靠 profiling 数据，靠现有工具的公开物证。访谈还能反过来发现 A1–A8 自身的缺陷（比如 FR-8 单条启发式覆盖不了 free 型空闲这个已经暴露出来的问题）。

**审稿人会怎么攻击**：① 「自设考卷自己满分」——A1–A8 出自本 PRD，作者定标准又自己达标，这是最会被攻击的一点；缓解：把 A1–A8 追溯到参照系的独立条款、请第三方专家在看到工具之前先对验收项本身表态是否合理。② n 小且部分专家与作者同组织 → 利益相关必须披露，第三方专家的判定单独报。③ 第一段的截图取证有 cherry-picking 风险 → 需给出检索协议（查了哪些工具、哪些版本、排除了什么）而不是只放支持性的例子。④ 符合性 ≠ 有用性：通过 A1–A8 只说明不犯已知错误，不说明用户能更快完成任务——仍需设计 #1 兜底。

### 预注册的误判诱发实验（misconception elicitation，专补 P1/P2/P3）
**工期**：4–6 周（题目设计与第三方审题 2 周 + 预实验 1 周 + 执行 1–2 周 + 分析 1 周）。因为不含任何真实 profiling 数据，可以在合规审批未落地时先跑，是「合规卡住则全盘停摆」这个风险的对冲。

**设计**：完全不依赖 B 仓库数据，直接打 PRD §11 的北极星。构造一组带陷阱的配置任务，每题问一个可判对错的事实：
(a) 给一份 Ulysses CP 的配置，图上出现 All-to-All，问「这是 MoE 吗」——测 P1；
(b) 给一份写着「SP=4」的配置，问「切的是哪一维、插的是什么原语」——测 SP 双语义（参照系 §00 术语表列为必须区分的三条之一）；
(c) 给 CP=2、DP=4 两份配置，问「这两张图哪张是模型分布、哪张是输入分布」——测 P2；
(d) 一卡多 device 的场景，问「rank 5 装着什么」——测 P3；
(e) 把 DP 从 2 调到 8，问「单卡显存会怎么变」——测 A3（正确答案：不变）。
条件 A = 现有工具，条件 B = 本框架。预注册题目、判分标准与分析计划；题目由第三方审题防止作者把陷阱设得对自己有利。

**能证明**：P1/P2/P3 三类错误的**存在性与可消除性**——恰好是 B 仓库那批数据完全覆盖不到的三条，也恰好是 PRD 认定的「与现有方案的全部差别所在」（M1 完成定义里的 A1/A2/A4/A6/A7）。它直接产出误判率这个数，且不受合规审批阻塞（无实测数据）。

**审稿人会怎么攻击**：① 生态效度——人造陷阱配置不是真实工作，审稿人会问「真有人会在真实项目里犯这个错吗」；缓解：陷阱来自参照系 §13 记录的真实勘误（该文档自承曾把维度与原语写成一一对应），以及框架文档/教程中的实例，附出处。② 陷阱题由作者设计 → 预注册 + 第三方审题 + 公开题库。③ 「被试是新人所以答错」的替代解释 → 分层招募并报经验年限的调节效应。④ 与设计 #1 的结果如果不一致（合成任务上有差、真实任务上没差）需要在 discussion 里正面处理，不能只报好看的那一半。

### 数值一致性校验（artifact 可信度门槛，非贡献但必须做）
**工期**：1–2 周解析与断言（前提是取数成功）；取数本身的周期不可控，取决于 B 仓库作者与合规。建议第一周就发起取数请求，与设计 #2/#4 并行。

**设计**：回 B 仓库作者处取 level2 数据集的原始 4 个 *_ascend_pt 目录（这是全批唯一有公开来源链接的数据集：gitcode msinsight-quick-start-demo 的 level2.rar，合规最干净），完整接入本框架的解析层，然后逐项断言本框架自己算出来的数与 msprof-analyze 的权威口径一致：computation 231.3/230.9/400.4/401.1 ms、communicationWaitStageTime 318.3/339.9/175.8/159.7 ms、transmit ~101.8 ms/卡、stepTime 809.9–810.8 ms、PP bubble 率 39%、Overlapped=0。任何一项对不上都必须查到原因并公开记录。

同一流程顺带做数据溯源清理：md5 记录每个输入文件、拒绝接受无法回源的二手数值（pangu 那份因此被自动排除）。

**能证明**：证明「本框架的数字不是抄报告抄来的，是自己从原始 trace 算出来的，且与业界工具口径一致」。它本身不是学术贡献，但它是把这批材料从 data source 升级为可信 artifact 的**门槛**——没有它，前面四项设计里所有涉及真实数据的部分都会被质疑数据通路是手工录入。同时它是对 pangu 那类数据完整性事故的制度性防线。

**审稿人会怎么攻击**：① 审稿人视之为最低要求而非结果，不会因此加分——所以放 artifact appendix，不要放 evaluation 章节。② 只在一个数据集上验证，覆盖面窄；② 若解析结果与报告数字不一致，必须如实写进论文（这反而是加分项，可与 verl 报告那次公开自我订正——通信子项 57%→33%，因口径从逐 op 平均带宽换成字节加权——并列写进 methodology，讲口径如何决定结论）。③ 取不到原始数据则整项作废，届时只能明确声明「本文使用的 per-rank 数值转录自 [报告]，非本工具解析」，并接受随之而来的可信度折扣。

## 5. circularity 风险（为什么这套嫁接方案容易被审稿人一眼看穿）

高，而且是最容易被一眼看穿的那一型：结论先在，框架后到，命中是选样的结果而不是框架的功劳。

具体怎么被看穿：

(1) 事后合理化的标准形态。报告先有结论（PP 末级过载 / rank15 host 饿死），A 框架的 P4/DP-3 再去「命中」它。审稿人会问反问句：如果结论不是这个，你的框架还能不能命中？答案就在同一批数据里——eta_eager 那份（单卡推理、92.6% device idle、IndexPut 落 AI_CPU、NonZero 触发 D2H 同步单次 72 ms）与 P1–P4 一条都不沾；ascend_analysis_20260527（单算子 simulator、cube 利用率 65%、GM 往返 5.24 MB）同样一条不沾；MultiProf 的真根因（8390 次在线编译 + 40.4% AICPU 算子）也落在框架作用域之外。8 份报告里能被 P1–P4 触及的只有 3 份（且都只触及 P4 一条）。命中率 3/8，而且是挑出来的那 3 份。

(2) 更致命的一处，就写在报告正文里。每份报告的每个问题点都自带一栏「问题举证视图」，指名的是 **MindStudio Insight 的既有视图**（Timeline 视图（系统调优）/ 算子视图 / 通信视图 / 详情视图 / 内存视图 / 源码视图），并写明载入哪个文件、看哪一段。也就是说：这批 incident 已经被现有工具的现有视图解释清楚了，而且解释路径是明确、可复现、写下来的。拿它们去论证「需要一套新的并行拓扑视图」，等于自己举证了 baseline 已经够用。这一条不需要审稿人多聪明，报告自己招了。

(3) 附带的方向性问题：报告的「视图推荐」是由一个叫 msinsight-view-selector 的 skill 自动生成的。若论文声称「本框架的视图能覆盖这些问题」，实际是在跟一个自动生成的视图推荐清单比对，而那份清单的分类体系与本框架的五视图/五图层不是同一套本体——比对结果会既不严谨也不可解释。

唯一能跳出循环的路子只有一条，而且要在方法上讲清楚：**把这些报告当 ground truth，不当结论**。即：报告里的结论是「标准答案」，报告里的证据链是「专家用旧路径走完的轨迹」，然后拿新路径去跟它比正确率与耗时（见 legitimateStudyDesigns #1）。答案由 B 仓库提供、由第三方专家复核，框架去做的是「多快多准地重走到同一个答案」。这样一来数据的来源（另一套工具）从缺陷变成了优点——它保证了标准答案不是本框架自己定的。
