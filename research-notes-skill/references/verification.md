# 怎么拿到一手源（操作技巧）

核实的成败往往不在"想不想核"，而在"能不能真的把一手材料读到手上"。搜索引擎摘要和二手博客是最容易骗人的——它们经常把某个版本的实现说成通例，或者转述时丢掉关键限定。下面是几条实操路径和会踩的坑。

## 优先级

**源码 > 论文原文 > 官方文档 > 二手解读**

源码排第一，是因为它不会撒谎也不会过时——它就是正在运行的那个东西。论文次之（描述的是作者当时的实现）。官方文档常滞后于代码。技术博客只能当线索，不能当依据。

## 源码

### GitHub 网页链接抓不到，用 raw

`WebFetch` 抓 `github.com/<org>/<repo>/blob/...` 会被 robots.txt 拒绝。改用 raw 域名直接下载：

```bash
curl -sL https://raw.githubusercontent.com/<org>/<repo>/<branch>/<path> -o /tmp/file.py
```

下载后用 `grep -n` 定位、`sed -n 'A,Bp'` 读片段，比在网页上翻快得多，也方便引用行号。

### 定位技巧

先 grep 关键词摸清结构，再精读相关段落，不要一上来通读几千行：

```bash
grep -n "关键词" /tmp/file.py | head -40      # 先看有哪些命中
sed -n '600,700p' /tmp/file.py                 # 再精读
```

函数的 **docstring 常常是最高质量的一手依据**——作者会在里面写清楚设计意图、编号规则、举例说明。这类内容比读实现代码更适合直接引用进笔记。

### 引用格式

标注到**文件名 + 行号**，这样后来的人能一步跳回去：

```markdown
> 源码印证：默认 `order = "tp-cp-ep-dp-pp"` —— Megatron-LM `parallel_state.py:617`
```

## 论文

- arXiv 有稳定的 abs / pdf 链接，引用时带上编号（如 `arXiv:2505.21411`）而不只是标题——标题会重名，编号不会。
- 引用具体数据时定位到 **Table / Figure / 章节号**，别只写"论文里说"。
- 注意版本号（v1/v2），数据可能在改版时变过。

## 官方文档

适合查 API 签名、参数含义、术语定义。但涉及"默认行为""内部实现"时要警惕滞后——这类问题回到源码确认。

## 证据分五档

"已核实 / 未核实"这个二分太粗。实际核实时会遇到一种很常见的中间态：**你能确认某份官方文档存在、章节标题就是你要的那个，但正文需要登录或被 robots 拦住**。这种情况既不是"核实了"，也不该和"我猜的"混在一起——它的价值在于给了后来的人一个精确的去处。

| 档位 | 含义 | 笔记里怎么写 |
|---|---|---|
| ✅ 已核实-原文 | 读到了原文本身 | 附文件名:行号 / 章节号 / Table 号 |
| 📄 标题级 | 确认文档与章节存在，正文抓不到 | 附文档编号 + 章节名，注明"需登录" |
| 🔍 第三方分析 | 多个独立来源说法一致 | 注明"多源一致"并列出来源 |
| ⚠️ 单一来源 | 只有一处说过，未能交叉验证 | 明确写"引用需谨慎" |
| 🔸 推断 | 基于同类产品或逻辑推导 | 写清推断依据，别只写结论 |

中间三档最容易被偷懒合并成"已核实"。别合——它们在后续决策里的分量差别很大，尤其当有人要拿这条结论去做设计或对外讲的时候。

## 数字要自己算一遍

材料里的数字经常互相矛盾，而且**光看单个数字看不出来**。凡是能相乘相除对上的量（设备数 × 端口数 = 连接总数 这类），至少用两条独立路径各算一遍。

真实案例：一份材料同时写着"每节点 7 个光口"和"全系统 5,376 条连接"。48 个节点 × 7 = 336，和 5,376 差了 16 倍。换一条路径算——56 台交换机 × 2 颗芯片 × 48 条 = 5,376——才发现每节点其实是 112 条，"7 个口"说的是平面数不是端口数。

**把算式留在笔记里**，不只写结论。后来的人一眼能复核，也能在材料更新时快速发现哪里对不上：

```markdown
每节点上行 112 条 = 7 平面 × 16 颗/平面
全系统 48 × 112 = 5,376
另一条路径：56 台 × 2 芯片 × 48 = 5,376 ✓ 两种算法一致
```

## 零命中也是发现

搜了半天什么都没找到，这本身是有价值的信息——它告诉后来的人"别再白搜一遍了"。

所以要**具体记录搜索过程**：搜了哪些精确短语、在哪些站点、结果如何。写"公开资料未找到"没用；写"精确短语搜索『灵衢互联刀片』『IO转换刀片』『NPU计算刀片』在中英文搜索引擎均零命中，openUBMC 社区论坛站内也无结果"才有用——它同时说明了这个说法很可能是内部命名，以及下一步该去哪找。

## 交叉验证

同一个论断如果能在两个独立来源上对上（比如源码 + 论文），可信度显著提升，值得在笔记里注明"两处一致"。

如果两个来源**打架**，这本身就是重要发现，写进笔记：说明分歧在哪、你采信哪个、为什么。

## 抓不到的几种典型形态

核实卡住时，先分清是哪一种——处理方式完全不同：

| 形态 | 症状 | 怎么办 |
|---|---|---|
| **robots 拒绝** | GitHub blob 页、部分知识社区 | 换 raw 域名；换镜像站；社区内容常有转载版 |
| **需登录** | 企业支持站返回 403 | 记到"标题级"，并把文档编号写进笔记，方便有账号的人去取 |
| **JS 渲染** | 抓下来只有表头没有行、只有骨架没内容 | 说明白哪部分没取到，直接向用户要那一块；别拿抓到的残缺部分当全部 |
| **纯 JS 应用** | 3D 展示页、交互式图表 | 记下 URL 和"需要能跑 JS 的浏览器打开"，作为待深化线索 |

关键是**别把"抓不到"写成"不存在"**。这两件事在笔记里的含义天差地别。

## 内部口径和公开资料打架时

用户提供的内部说法与公开数据冲突，是很常见的情况——尤其涉及产品内部命名、单板划分、代号这类信息。

不要偷偷采信任何一方。做成对照表：

| 内部口径 | 公开资料能印证什么 | 核对结果 |
|---|---|---|
| NPU 计算刀片 × 8 | 每节点确为 8 颗（384÷48） | ✓ 对得上 |
| CPU 计算刀片 × 8 | 每节点为 4 颗（192÷48） | ✗ 对不上，需现场确认 |

然后做三件事：**给出可能的调和解释**（是槽位数？是别的型号？是代际差异？）、**明确标出哪一条需要现场确认**、**把这类核对记录放进附录**——因为它是调研过程记录，不是知识，放在正文会打断连贯性，而且大量"零命中/待核实"读起来很挫败。

## 什么时候该停下来标"未核实"

核实是有成本的。以下情况直接标注、不要硬钻：

- 需要读的源码在私有仓库或需要登录
- 论文只有摘要可读，正文在付费墙后
- 结论依赖于用户内部环境的具体配置
- 挖下去会明显偏离当前主题

标注要**具体**，写清缺什么、下一步怎么补，这样它就变成了"待深化"里一条可执行的线索，而不是一句含糊的免责声明：

```markdown
⚠️ **未核实**：推测 EP 组按连续 rank 划分。需读 `RankGenerator` 的 expert_order
注入逻辑确认，本轮未展开。
```

## 反过来也要核

用户提供的分析、别人的博客解读、以及**你自己整理时形成的直觉**，都要走同一套核实流程。

用户的说法经核实站得住时，值得在笔记里点明"已核实"——这会让他更敢用自己的判断。经核实有偏差时，把正确的写清楚并说明差在哪，这比默默照抄有价值得多。
