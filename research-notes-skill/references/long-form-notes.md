# 笔记长成手册之后（长文档 / 可交互笔记）

单篇笔记不需要操心这些。但当一条研究线索攒到几十节、几十张图、还要拿去和别人对齐认知时，下面这些问题会反复咬人。

## 载体：什么时候该从 Markdown 换成单文件 HTML

Markdown 是默认选择，够用就别换。但有两类情况换成**单文件 HTML**（内联所有 CSS/JS，不依赖外部资源）收益明显：

1. **结构本身就是内容**——网络拓扑、协议分层、物理层级、状态机。这类东西用 SVG 画出来，读者一眼就懂；压成文字描述就等于把信息扔了。
2. **要给别人看**——需要目录导航、深浅色切换、可展开的分支说明、故障注入之类的演示能力。

单文件的好处是可以直接发给人、离线打开、不会因为图片链接失效而残缺。

### 交互内容的致命陷阱

**藏在点击后面的内容会被 100% 漏读。**打印、纸面阅读、快速扫读的人根本不会去点。

这个坑踩过一次：故障定位的完整排查链条只存在于交互面板的 JS 数据里，点了按钮才看得到——而那恰恰是整篇最有价值、最该被照着做的内容。

规矩很简单：**交互只用来增强，不用来承载。**任何"照着做"或"必须知道"的内容，正文里必须有一份完整副本；交互面板做的是让它更好懂，不是它唯一的存在形式。

### 图必须渲染出来看一眼

SVG 文字重叠、超出边框、被后画的矩形盖住——**这些都不会报错**。控制台干干净净，图却没法看。

所以生成图之后一定要真的渲染成截图看一遍。常见毛病就那几种，看一眼全能发现：

- 标签和另一个标签在同一行重叠（尤其居中标签与右对齐标签相遇）
- 文字长度超出所在矩形（中文按每字约 10–11px、英文约 5.5px 粗估宽度）
- 后画的元素盖住先画的文字（表格斑马纹背景盖住表头是经典）
- 连线穿过标签文字

## 文字说不清时，问题往往是视觉缺位

当用户说"看不懂"或"没看出来"时，第一反应不应该是加更多文字解释。**先问：这里有没有一张图？如果有，图画对了吗？**

经验：用户说"没有看出来浪费在哪里"，问题不是文字解释不够详细——而是图里用了灰色占位块，没有直观展示"浪费"长什么样。把灰色块换成和原图一样的着色方案（让两种情况可以直接视觉对比），再加一条红色标注指出差异，用户一看就懂了。

**判断流程：**

1. 用户说"看不懂" → 先看这个概念有没有配图
2. 没有配图 → 问自己：这个概念的本质是空间关系/数量对比/流程步骤？如果是，加一张图
3. 有图但看不懂 → 不是加文字的问题，是**图本身要改**。常见原因：
   - 对比项没有用同一套视觉语言（颜色/形状），读者无法直觉地"对齐"
   - 差异太微妙，需要显式标注（箭头、红色高亮、括号注释）
   - 两种状态并排时比例失真，量级差异被抹平了
4. 有图且图是对的 → 这时再考虑加文字

### 视觉解释的第一版几乎一定要返工

接受这个事实：图解和代码不一样，**没有编译器帮你查错**。图上的每一个视觉元素——颜色、大小、位置、标签——都在传递信息，而你不一定传对了。

常见的第一版问题：

- **视觉重点和认知重点不一致**——你觉得重要的东西画大了/着色了，但读者想看的是另一个维度
- **对比项的视觉相似度太高**——两种状态看起来差不多，读者找不到差异在哪
- **缺少"读图路线"**——大图上没有标注从哪看起、按什么顺序看
- **用了需要图例才能解读的编码**——颜色 A 代表什么只写在角落的图例里，读者要来回跳

**补救办法不是给图加说明文字，而是改图本身：**

- 直接在图上标注差异（"这里比那里多了 2×"，而不是在文字里写"注意上下两行的区别"）
- 用括号/标尺等空间元素把对比关系可视化
- 给最重要的差异加上颜色对比（红/灰 或 有/无）

## 编号：不要手工维护

反复插入新章节、新图之后，手工维护的编号一定会乱——跳号、重号、附录里还留着旧号、正文引用指向错的图。

**做法：编号在最后按文档位置统一生成。**写作过程中用占位符（`FIG A`、`FIG B`）或临时号，最后扫一遍文档、按出现顺序重排。同一次操作里把正文里的交叉引用一起改掉。

章节重排同理。物理调整章节顺序时要一次性处理：section id、标题号、导航、小节号（3.1→7.1）、正文里所有 `§NN.M` 交叉引用。用"先全部换成占位符、再统一映射"的两步法，避免边替换边被后续规则二次命中。改完做一次**锚点体检**：遍历所有内部链接，确认每个都能找到目标。

## 术语统一：写完之后要专门扫一遍

两类问题在长文档里几乎必然出现，而且靠"写的时候注意"防不住，必须事后专门扫：

**同词多义。**同一个词在不同章节指不同东西。判断方法：把这个词的所有出现拉出来看一遍。修的时候不是逐处改措辞，而是**先定死一个用法，然后全篇统一**，并在开头留一张用语对照表：

| 本手册用语 | 指什么 | 数量 | 别名 / 易混点 |
|---|---|---|---|
| 计算节点 | 一台物理机箱，含 N 张卡 | 48 个 | 也叫"计算框"。**不是一张卡** |

**同形编号撞车。**硬件分 L1/L2、软件栈分 L1–L4、通信视角分 L2–L5——三套 "L" 编号在同一份文档里。这时主动改写其中一套（软件栈改 ①②③④ 最省事，因为它本来就是层次而非专名），并留一段三套编号的辨析表。不改的代价是读者每次看到 "L2" 都要停下来猜。

## 章节顺序：用引用方向体检

长文档最隐蔽的结构问题是**前向引用倒置**——某一节的内容大量指向后面还没读到的章节，读者被迫跳着看。

体检方法很直接：统计每节的交叉引用指向前面还是后面。**某一节如果绝大多数引用都指向后面，它的实际功能是目录而不是内容**，位置错了。

两种修法：

- **物理重排**——效果最好，但交叉引用多的时候是个大工程，要按上面"编号"那节的两步法做，并做锚点体检。
- **原地加读法提示**——成本低。明确写"这一节是地图，读完 X–Y 之后回来读第二遍"。如果暂时不方便重排，这能拿到大部分效果。

顺带一个便宜的技巧：某一节大量依赖后面才讲的组件名时，在该节开头放一张**组件迷你表**（每个一句话），读者就不用跳走了。

## 概念间关系：要专门画，不能指望读者自己拼

当文档里有三个以上相关概念时，单独讲清每个概念远远不够——读者脑子里拼不出它们之间的关系。

**在所有概念分别写完之后，专门留一节画关系图。** 三种方式：

1. **对比表**——同一组维度（作用对象 / 操作方式 / 代价 / 收益），逐行写。读者横向扫一眼就知道谁和谁像、谁和谁互补。
2. **变换链**——如果这些概念是对同一个对象的逐步变换，用基准记号写出"原始 → 经过 A → 经过 B → 经过 C"的完整链条，让读者看到叠加效果。
3. **正交性矩阵**——概念两两组合是什么效果（可叠加 / 互斥 / 独立 / 有依赖），画成小表。这张表对"我的场景下该开哪几个"这种决策价值最大。

经验：关系图画完之后，经常能发现单独讲的时候没注意到的事——比如两个看起来独立的概念其实共享同一组资源，或者两个看起来互斥的概念其实可以正交叠加。这些发现本身就值得回去补进各自的单独章节。

## 从材料反推真实问题

整理运维手册、SOP、故障处理文档这类材料时，有一个高价值的分析动作：**警告语气是痛点的化石。**

原文里以"注意事项"口吻写的东西，把口吻换成"用户痛苦"，往往就是真问题：

| 原文 | 反推出的痛点 |
|---|---|
| "官方 FAQ 给的排查链条**要背下来**" | 关键知识只存在于人脑里，没沉淀成工具 |
| "清理脚本必须**白名单式**而非黑名单式" | 这个语气说明历史上误删过 |
| "**不要用网上流传的**阈值数字"（出现三次） | 判定阈值没有权威且可及的来源 |
| "批量工具跑一半失败是常态" | 没有断点续跑 |

把这些整理成"原文 / 出处 / 反推出的痛点 / 待验证的问题"四列表。注意最后一列——反推出的是**假设**不是结论，要标清楚，并给出怎么验证。

## 读者换了，缺的拼图就换了

同一份材料，给不同的人看，"完整"的定义不一样。技术笔记天然会把机制写满，但对非研发读者，缺的往往是**一个字都没写**的那类东西：

- **谁**——买的人、装的人、用的人、运维的人，各自怕什么、成功标准是什么
- **多久**——一步要多久、整件事要多久、哪里在等
- **多大代价**——做错了业务侧感受到什么，可不可逆
- **现在怎么干**——不引入新东西的话，他们今天是怎么解决的，哪里最难受
- **怎么算好**——有哪些行业通用指标，目标值从哪来

发现缺了这些，不要用推理补（见 SKILL.md"缺一手数据时"那条）。搭好结构、留空、附问题清单。
