# 技术研究学习笔记整理

## 这个技能要解决的问题

把资料"总结一下"是容易的，模型天然就会。但**总结不等于笔记**。

一次性的总结读完就扔；而研究笔记是要在几周、几个月后被反复翻回来的，它要能承接后续资料、要能被信任、要能让人在忘光之后靠它快速回到当时的理解深度。这中间的差距，就是这个技能要补的：

- **可累积**：笔记是有编号的一个系列，后一篇能引用前一篇，索引始终是最新的。
- **可信任**：关键论断标注出处；核实不了的显式标"未核实"，而不是混在权威内容里蒙混过关。
- **可回到现场**：图解的层次结构、抽象概念的具体算例、当时没搞懂的问题，都留在笔记里。

写笔记时始终想着一个读者：**三个月后已经忘光了的用户本人**。他会问"这个结论靠谱吗、从哪来的"、"这段图当时长什么样"、"我当时卡在哪"。笔记要答得上来。

**但也要留意读者会换。** 同一份材料，给研发看和给设计师、产品看，缺的拼图完全不同——技术笔记天然会写满机制，却写不出"谁在用、一步要多久、做错了谁疼、现在他们怎么干"。所以在动笔前和交付时各问一次：**这份笔记的读者要拿它做什么决定？** 读者一变，"完整"的定义就变了，该补的往往是原来一个字都没写的那类东西。

## 流程

### 第 1 步：先看已有的笔记

**在动笔之前**，先列出笔记存放目录，看看这条线索已经有哪些笔记。这一步不能跳，因为它决定了三件事：

- 新笔记的**编号**（接续，不重号）
- 新内容和已有内容的**关系**（是深化某篇？修正某篇？还是新开一支？）
- 有没有**需要回头修正**的旧结论（新资料推翻了旧笔记里的说法时，回去改，别让错的留着）

如果有项目记忆（project memory）或索引文件，一并读了——里面常有"用户约定的工作方式"和"已核实事实"这类不在笔记正文里的上下文。

如果目录里一篇都没有，那就是笔记 01，同时准备建索引。

### 第 2 步：核实（这一步是强制的）

用户要的是**能信的笔记**，所以任何会被当成事实引用的论断，都要么附一手源，要么标明证据强度。不能省略。

核实的优先级：**源码 > 论文原文 > 官方文档 > 技术博客/二手解读**。

尤其注意：**不要只看搜索结果摘要就下结论**。搜索摘要经常是二手转述，而且常年过时。真要确认一个机制，就去把源码 clone 或 curl 下来读、把论文对应章节调出来看。`references/verification.md` 里有具体怎么拿到一手源的操作技巧（含几个会踩的坑），核实时读一下。

**证据分五档，不是两档。** "已核实/未核实"这个二分太粗，会把"看得到文档标题但正文抓不到"和"纯粹是我猜的"混为一谈，而这两者在后续决策里的分量完全不同：

```markdown
✅ 已核实-原文      读到了原文本身
📄 标题级           确认了官方文档/章节存在，但正文需登录或抓不到
🔍 第三方分析       多个独立来源说法一致
⚠️ 单一来源         只有一处说过，未能交叉验证，引用需谨慎
🔸 推断             基于同类产品或逻辑推导，公开资料未覆盖
```

标注要具体到位置：`Megatron-LM parallel_state.py:617`、`arXiv 2505.21411 Table 3`、`EDOC1100401572 §灵衢总线设备（标题级）`。

**数字必须自己闭环。** 凡是能相乘相除对上的数字，至少用两条独立路径各算一遍再写进笔记，并且**把算式留在笔记里**而不只写结论。同一份材料里出现互相矛盾的数字是常事，光看单个数字看不出来。这个动作至少两次救过场：一次是发现原始材料里两组数字根本乘不通；一次是发现自己写的两处口径不一致。算式留在笔记里，后来的人一眼能复核。

**区分"一次性动作"和"持续过程"。** 很多机制容易搞混"做一次、效果持续"和"每一步都在做"。比如：一个初始化阶段的切分，切完之后后续所有阶段都在用切分后的结果——这是"一次性动作，效果持续"；而某种通信操作每一步都在做——这是"持续过程"。如果笔记里只写"X 把数据切了"，读者会搞不清到底是每步切一次还是只切一次。所以在描述机制时，**显式写清"发生在哪里"和"效果持续到哪里"**——这两件事经常不同，而误解恰恰出在这里。

**用户自己提供的分析也要核。** 如果发现用户的说法有偏差，**在笔记里把正确的写清楚，并说明差在哪**——这比默默照抄有价值得多。反过来，如果用户的直觉经核实是对的，也值得点明"已核实站得住"，他下次会更敢用这个直觉。

内部口径和公开资料打架时，不要偷偷采信任何一方：做成对照表（内部说法 / 公开数据 / 核对结果），给出可能的调和解释，并明确标出需要现场确认的那一条。

### 第 3 步：写笔记

用下面的模板。不是每篇都要写满所有段落——没有图解就不写图解那节——但**开头的一句话结论、证据标注、末尾的待深化**这三样每篇都要有。

模板见下一节。写的时候注意这几件事：

**保留图的层次结构。** 如果资料里有架构图（哪怕是 OCR 出来的乱码文本），不要只用散文描述它"讲了什么"，要用代码块把它的**层次和嵌套关系**画出来。图的形式本身携带信息——什么套在什么里面、什么和什么并列、箭头往哪走——这些在散文里会丢失，而这恰恰是几个月后最想回看的东西。

```
第 1 层：DP Replica 0 ... D-1          ← 横向并排的完整副本
  └─ 第 2 层：PP Stage 0→1→2→3         ← 流水线箭头串联
       └─ 第 3 层：TP Group (size=4)    ← 标注具体 GPU 编号
```

**给抽象概念配一个能手算的例子。** 一个具体到能自己验算的小例子，胜过三段定义。比如讲编号规则，就给具体参数值，把某个实例拆解成各维度分量，再列出它所属的组。读者自己一算就懂了，而且能验证你没写错。

**找到领域的基准记号，全篇贯穿。** 每个技术领域都有一种最自然的"坐标系"——一套记号，用它来写每个概念时，概念之间的关系就能**算出来**而不只是描述。整理笔记时先找到它，然后全篇一律用它锚定。

怎么找：问自己"这个领域里，**所有概念都在改变的那个东西**是什么？"那个被改变的东西的表示方式，就是候选的基准记号。好的基准记号满足三条：① 每个概念都能用它写一个"前→后"变换；② 两个概念叠加后的结果能从记号里推算出来；③ 读者看到记号就知道大小/方向/性质的变化。

找不到完美的，选一个最接近的，在笔记开头说清用法。有了它，后续所有概念就不再是孤立的散文段落，而是同一坐标系里的不同操作——可以对比、可以叠加、可以验算。

**术语先统一，再写正文。** 技术领域里两个陷阱几乎必然出现，而且一旦漏掉，整篇笔记的可信度会被读者一次性怀疑：

- **同一个词指不同东西**——"节点"到底是一台机箱还是一张卡？先定死一个用法，在笔记开头列出用语对照表（本手册用什么词 / 指什么 / 别名与易混点），然后全篇扫一遍统一，别让两种用法并存。
- **两套同形编号撞车**——同一份材料里，硬件分 L1/L2、软件栈也分 L1–L4、通信视角还有 L2–L5。这时**主动改写其中一套**（比如软件栈改成 ①②③④），并留一段换算说明。不改写的代价是读者每次看到 "L2" 都要停下来猜。

**显式纠正误解。** 如果这个主题有常见的理解陷阱（尤其是用户自己踩过的、或者你整理时才发现方向反了的），单独立一节写"❌ 常见误解 / ✅ 正确机制"。这类内容的价值密度最高。

主动打掉误解比正面陈述更有效：先说清楚正确机制，再列两条"✗ 常见误解一 / ✗ 常见误解二"，读者会拿自己的理解去对照。

**"什么时候不用"比"什么时候用"更清晰。** 解释一个机制或工具的适用场景时，正面罗列十个使用场景常常越讲越迷糊——读者在每一个场景上都在想"那我的情况算不算"。反面一句话"它在 X 条件下完全没有意义"往往更快收敛。

更一般地：**如果一个机制的正确答案是"它几乎总是开着"或"它只在极端条件下才有用"，那么"什么时候用"这个问题框架本身就在误导。**改为讲清代价和收益的净效果——代价为零则永远开，代价不为零则算 break-even point——读者自己就能判断了。

**概念间关系比单独概念更值钱。** 单独讲 A 和单独讲 B 都不难，但让读者从"知道"变成"理解"的，是画清它们之间的关系——同一个对象的不同操作？效果叠加还是互斥？必须一起用还是彼此独立？

三种画法：

1. **对比表**：同一组维度逐行写（切什么 / 切几份 / 代价 / 收益），读者一扫就看出异同
2. **变换链**：用基准记号把概念串起来，写出数据经过每个概念后的状态变化
3. **正交性矩阵**：N 个概念两两组合是什么效果（叠加 / 互斥 / 独立），小表就能画清

**成本-收益是万能分析框。** 几乎任何技术机制都可以用三句话讲清本质：它**花了什么代价**（通信、计算、复杂度、内存）、**换来什么收益**（吞吐、可扩展性、可维护性）、**净效果是什么**（总是值得 / 有条件值得 / break-even point 在哪）。

把这三句话作为每个机制描述的标准收尾段。读者看完原理后，看到成本-收益就能自己做决策——"我的场景下该不该用这个"。代价为零的机制直接标"免费，无条件开"；代价不为零的，给出 break-even 条件。

**记下例外和边界。** 理想模型总有不成立的地方（"这六个维度其实只有四个真正正交"）。这些例外是后面做设计时最容易翻车的点，必须写进去，别为了模型漂亮而隐去。

**缺一手数据时，交付"采集它的工具"，而不是猜。** 有些字段（真实耗时、现场怎么干、故障频率）只能从人身上拿。这时不要用推理填满，而是把结构搭好、字段留空并标"待填"，同时附一份**可以直接拿去问人的问题清单**。一份好的问题清单比十条推断有用，而且它把这一节从"欠着"变成了"有下一步"。

**待深化写成 checkbox。** 当时没查清的、存疑的、下一步要挖的，都列出来。这是下次接着做的入口。

### 第 3.5 步：把对话问答沉淀回笔记

用户的**提问本身就是笔记最该补的地方的精确定位器**。

经验：用户在对话里的概念性提问——"X 是不是只在 Y 阶段出现？""A 和 B 是什么关系？""什么情况下会用 C？"——每一个都精准指向笔记里的知识空洞。回答经核实后不应只留在对话里，而要**补回笔记的对应位置**。

模式识别：

- **"X 是不是只在 Y 出现？"** → 笔记写了 X 的机制，但没写 X 的作用范围/生命周期。补：X 在哪里生效、效果持续到哪里。
- **"A 和 B 什么关系？"** → 两个概念各自讲了，但关系没画。补：对比表或变换链。
- **"什么时候用 C？"** → 缺成本-收益分析。补：代价、收益、净效果。
- **"我看不懂这张图"** → 不是文字解释不够，是**视觉表达出了问题**。这时候加文字没用，要修图或重画图（见 `references/long-form-notes.md` 的"文字说不清时"那节）。

做法：

1. 在对话里回答概念问题时，同时判断：这个回答三个月后还会被翻回来吗？
2. 如果是，回答完立刻补进笔记，别等"下次整理时一起补"——你会忘。
3. 补进去时，不要原样搬对话，而是按笔记的格式（基准记号、证据标注、手算示例）重新写。对话是即兴的，笔记要耐看。
4. 如果同一轮对话里连续冒出三个以上的概念问题，说明这个主题值得单开一篇笔记，而不是逐条补丁。

**连续提问暴露渐进深化结构。** 如果用户先问"A 是什么"，再问"A 和 B 什么关系"，再问"什么时候该用 A"——这不是三个独立问题，而是同一个认知在三个层次上展开：**概念 → 关系 → 决策**。这个三层结构本身就是一篇好笔记的骨架。

### 第 4 步：存盘 + 更新索引

- 笔记存进用户的项目/研究目录，文件名带编号和主题：`<研究线索>-学习笔记0N-<主题>.md`
- 用文件交付工具把笔记发给用户（Cowork 里是 `SendUserFile`；如果笔记要落到用户本地磁盘，再 `device_commit_files`）
- **更新索引**：如果有项目记忆或索引文件，把新笔记加进"已保存产物"列表，一句话说明这篇讲了什么。索引过期的笔记系列等于没有。
- 如果这轮核实出了新的关键事实（尤其是推翻旧认知的），也写进索引/记忆的"已核实事实"段，避免下次重复查。

## 笔记长成手册之后

一条研究线索攒久了，笔记可能从单篇 Markdown 长成几十节、几十张图、还要拿去给别人讲的东西。这时会冒出一批新问题：该不该换成可交互的单文件 HTML？图号和章节号怎么维护才不乱？藏在交互后面的内容会不会被漏读？章节顺序怎么排才不会逼读者跳着看？视觉解释第一版几乎一定要返工怎么办？

这些在单篇笔记阶段不必操心，但一旦规模上来就会反复咬人。需要时读 `references/long-form-notes.md`。

## 反模式

这几种情况说明笔记写偏了：

- **通篇散文复述资料**——没有表格、没有层次结构、没有算例，读起来像读后感。
- **论断不带出处也不标证据强度**——读者无法判断哪句能信，整篇的可信度归零。
- **图解被压成一段文字描述**——图的结构信息丢失，几个月后无法还原当时看到的东西。
- **编号重复或跳号、索引没更新**——系列失去累积性，找不到东西。
- **为了让模型显得漂亮而隐去例外**——这是最危险的，因为后面基于这个模型做设计时会翻车。
- **数字只抄不算**——材料里互相矛盾的数字原样搬进笔记，等着以后某个人发现。
- **术语混用**——同一个词在不同段落指不同东西，或两套同形编号并存却不作说明。
- **拿不到的数据用推理填满**——比留空更糟，因为它看起来像已知。
- **只讲单个概念、不画概念间关系**——读者知道了 A 和 B，但不知道 A+B 时会怎样。从"知道"到"理解"之间最大的断层在这里。
- **"什么时候用"列了十个场景但没讲代价和收益**——读者在每个场景上都在猜"那我的情况算不算"，不如直接告诉他判断公式。
- **混淆"一次性动作"和"持续过程"**——写"X 切了数据"但没说清是切一次还是每步都切，读者会猜错、而且猜错之后推导出的下游结论全都是错的。
- **对话里答得很好，但没补回笔记**——三个月后对话找不到了，答案等于没存在过。
- **文字解释不清时继续加文字**——有时候问题出在缺一张图或者图画错了，加再多文字也没用（见 long-form-notes "文字说不清时"）。
- **只答用户问的那一句就完事**——用户要的是能长期回看的笔记，不是聊天回复。

## 一个提醒

用户问了一个概念问题、你在对话里答得很好，这时候**答案本身往往就值得沉淀成笔记**——尤其当它是后续工作的基础模型时。不用等用户说"存一下"。但也别过度生产：一次性的小澄清、纯操作性的问答，留在对话里就够了。判断标准是：**这个内容三个月后还会被翻回来吗？**

反过来，用户随口问的"这个是什么意思""这里看不懂"，常常正指向笔记里最该补的那一块——他卡住的地方，三个月后的他还会卡。把答案补回笔记，而不是只在对话里说一遍。

**连续的概念问题是渐进深化的信号。** 如果用户在一轮对话里先问"A 是什么"，再问"A 和 B 什么关系"，再问"什么时候该用 A"——这不是三个独立的问题，而是同一个认知在三个层次上展开：**概念 → 关系 → 决策**。这个三层结构本身就是一篇好笔记的骨架。
