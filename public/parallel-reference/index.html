表 D · 卡 / device / 进程 / rank

全文的「卡」是刻意选的中性词——指一块独立的加速设备。并行切分、rank 排布、通信原语这些机制与具体厂商无关；平台差异只体现在互联名、集合通信库与算子栈的称呼上，不影响本文任何结论。

词指什么与 rank 的关系
物理卡插在机器上的那块板子不直接对应 rank
device驱动 / 运行时看到的逻辑设备，也是设备查询工具逐个列出的那个粒度rank 绑定的是它
进程训练脚本的一个实例默认一进程绑一 device
global_rank全局通信域内的编号默认与 device 1:1
「一张卡 = 一个 rank」对不对

对一半。准确说是两条：

  • device → global_rank 是 1:1（默认一进程绑一卡时）——这一半对。
  • device → rank 编号总数是 1:N——一张卡同时持有 global / tp / pp / dp / ep / cp / local 一整组编号。所以「一张卡一个 rank」只在 global 这一个域内成立，见 §10。

还有一层容易略过的精确性：rank 绑的是 device，不是物理卡。主流训练形态下二者重合——一块物理卡 = 一个 device = 一个 rank，日常混说没问题。但有的形态一块卡上带两个独立设备，那时「一张卡」就对应两个 rank。拿不准时以设备查询工具的实际列举为准——本文其余部分默认「一卡一 device 一 rank」的训练形态。

为什么 SP 值得单独强调

它的二义在中文语境里尤其容易翻车——「序列并行」四个字同时指向两个不同的并行维度、不同的通信原语、不同的嵌套位置。看到 SP 先问一句「是 Megatron 的还是 Ulysses 的」，能省掉一半的沟通成本。

基数：每种关系是几对几

后面所有关系里，最容易出错的不是「A 和 B 有关系」，而是「这个关系是几对几」。而且相当一部分关系的基数不是固定的——它随并行配置变化。本节先把记号钉死，再给出全景基数表；后文每处关系都会带上标记。

记号约定

1:1一一对应
1:N一对多
N:1多对一
N:M多对多
※基数随配置变化，见「取决于」列
  • 方向敏感。A → B 是 1:N 时，B → A 就是 N:1。本文一律按表头写的方向读，不省略箭头。
  • 区分类型与实例。「层」既可以指第 37 层这个实例，也可以指所有层共用的那份子图模板。两者对同一个 B 的基数往往不同，表里会写明。
  • N:M 不等于「说不清」。它是一个明确结论：两侧都能一对多，因此不存在归属关系，只能建索引。文中所有 N:M 都是这个意思。
第三格的陷阱

纯 TP 与纯 DP 在这张图上基数完全相同（都是层 → 卡 1:N），但语义相反：TP 的每张卡拿到的是碎片（单卡算不出这层的正确输出），DP 的每张卡拿到的是完整副本（单卡能独立算出）。基数相同不代表关系相同——判据在 §06 的那一列「能否独立算出这一层的输出」。

02

静态结构：整网怎么一路拆到硬件

整网是文章，层是句子，算子是词，kernel 是这个词在这块硬件上的发音。四级粒度，一条链。

算子：计算的最小语义单元

MatMul、Softmax、LayerNorm、Add、GeLU、Conv 这些。每个算子做一件明确的数学运算，输入张量、输出张量。它规定"要算什么"，不规定"怎么算"。

层：算子的固定组合模式 层 → 算子 1:N

一个 Transformer 的 Attention 层拆开就是：QKV 三个 MatMul → 转置 / reshape → QKᵀ MatMul → Scale → Softmax → 与 V 的 MatMul → 输出投影 MatMul。硬件眼里不存在"层"，只有一串算子。

但层不是纯粹的人为分组，它有一个硬性质：层与层之间的数据依赖极窄。上一层传给下一层的，只有一个 [batch, seq, hidden] 的激活张量；而层内部的中间张量又多又大——attention score 是 [batch, heads, seq, seq]，量级是 s² 对 s·h，长序列下差出一两个数量级。层间窄、层内宽，这才是层这个概念真正的物理基础，也是后面所有切分都以层为单位的原因。

整网：所有算子按数据依赖连成的那张图 整网 → 层 1:N

模型代码经框架（PyTorch / MindSpore）解析后，本质就是整网：节点是算子，边是张量的流动。训练时框架再自动补上每个算子对应的反向算子，整网规模翻倍。

结构上整网高度重复：embedding → Layer × N → lm_head。所谓 70 层、80 层就是这个 N。一层是整网的层子图模板，整网只是把同一份模板复制 N 份再串起来——权重不同，拓扑相同。

算子 ↔ kernel：接口与实现 N:M

算子 MatMul 规定输入两个张量、做矩阵乘、输出 shape 怎么推导；kernel 是这段语义在具体硬件上的一份实现代码——怎么分块、数据怎么在显存与片上 buffer 之间逐级搬运、计算单元怎么排流水。换硬件、换 dtype、换 shape，算子不变，kernel 要换。

关系基数成因后果
一算子 → 多 kernel1:Nfp16 / bf16、不同数据排布格式、大 shape / 小 shape 各有一份实现，编译期由算子选择挑一份同一算子改个 shape 性能就掉一截——选中的是另一份 kernel，或 tiling 不适配
多算子 → 一 kernelN:1算子融合：Add + LayerNorm + Cast 这类连续访存密集型算子合并中间结果留在片上不落 HBM，整网上节点变少但语义等价
一算子 → 多段 kernel1:N需要 workspace 的规约类算子必须分段执行profiling 的 kernel 计数与整网的节点数对不上，属正常

中间还隔着一层：tiling

kernel 不是拿到张量就能跑。执行前要先算 tiling——把大张量切成能塞进片上 buffer 的小块，决定循环怎么嵌套、搬运和计算怎么流水重叠。同一份 kernel 代码配不同 tiling 参数，性能能差几倍。静态 shape 可以编译期算好，动态 shape 得运行期算，这是动态 shape 性能往往不如静态的原因之一。

加上卡：它是这条链的第五级吗

不是。整网 → 层 → 算子 → kernel 是一条逻辑分解链，回答的是「谁包含谁」。卡是物理承载，它不在这条链上——它是另一条链的顶端：

逻辑侧    整网  →  层  →  算子  →  kernel
物理侧    卡    →  流  →  kernel 队列  →  kernel

通信算子恰好插在归属边界上，作用是把边界之上那部分「补齐」。边界推得越深，单卡自足的范围越小，需要补齐的东西越多，通信就越频繁。

先厘清 b：一个词，三个 batch

batch 的字面意思是「一次喂进网络的一组样本」。但在分布式训练里这个词至少指三个不同的量，混用会直接算错显存和吞吐：

名字是什么谁的视角
global batch size

micro-batch size
MBS		一张卡一次 forward 实际处理的样本数显存视角——激活体大小直接由它决定
gradient accumulation

GBS = MBS × GA × DP

b 这根轴被切了两刀，不是一刀。轴的全长是 GBS；DP 把它切成 DP 段，每段 GBS/DP；GA 再把每段切成 GA 份，每份才是 MBS。所以单卡在任一时刻手里的激活体，对应的是 MBS 个样本，不是 GBS/DP 个。

这解释了容器模型里那条最反直觉的结论

§08 会看到：把 DP 从 2 调到 8，卡数翻四倍，单卡容器却纹丝不动。原因就在这里——DP 动的是 GBS 那一刀，MBS 那一刀没动。激活体只认 MBS。所以「显存不够就加卡」只有在加的是 TP 或 PP 时才成立；加 DP 买的是吞吐，不是余量。

PP 的 micro-batch 与 GA 的 micro-batch 是同一批东西。流水线用来填气泡的那些 micro-batch，正是梯度累积的那些。由此得到一条 §11 依赖链里没单列的隐含约束：用 PP 时必须 GA ≥ PP，否则流水线根本填不满，气泡会占掉大半时间。

一条样本 = 一条序列。[B, S, H] 里 B 是样本数、S 是每条样本的 token 数。注意有些实现用 packing 把多条短文本拼进一条定长序列，这时 B 与「文档数」就不再一一对应了。

为什么 b 是五根轴里最便宜的一根

样本之间彼此完全独立——这是 DP 能成立的全部理由，也是 DP 通信最稀（整个 step 末才一次）的原因。对比另外四根：s 有 attention 的跨位置依赖、h 有矩阵乘的规约依赖、ℓ 有前后层的因果依赖、e 有路由依赖。b 是唯一一根「切开就不用管」的轴，所以 DP 是最省事、也总是最先被用满的并行。

先把两个对象说透：权重体与激活体

它们各自装的是什么

一个常见的近似说法是「权重体就是整网，激活体就是输入数据」。两处都差一点，而这两处恰好最容易出错。准确说是三样东西，不是两样：

是什么占多少显存被并行切吗
图结构：有哪些算子、怎么连、张量什么 shape。就是 §02 那条粒度链本身几乎不占不切——每张卡都持有完整的图定义
权重体状态：挂在图上的那些数值大头PP 切 ℓ · TP 切 h · EP 切 e

差的第一处：整网 ≠ 权重体。整网 = 图 ＋ 权重体。图说的是「怎么算」，权重体说的是「用什么数算」。图本身几乎不占显存，却决定了一切结构；而且图上很多节点根本没有权重——Softmax、Add、GeLU、Dropout 都是纯计算，一个参数也不带。

差的第二处（更要命）：输入数据 ≠ 激活体。输入只是入口：token id 是 [B, S] 的整数，256×8192 条 int32 也就 8 MB 量级。激活体是这些数据流过整网之后留下的全部中间结果，逐层堆积，量级是输入的几千倍。把「激活体」读成「输入数据」，会低估显存好几个数量级。

一个够用的类比

四条直接推论

一 · 共享轴决定了「谁能减什么」。ℓ 与 h 同时属于两个对象，b 与 s 只属于激活体。所以切 ℓ（PP）、切 h（TP）两边都减，切 b（DP）、切 s（CP）只动激活体。§08 容器模型那张表的四行，就是这句话的展开——不必另记。

二 · 生命周期决定了只有激活体能重算。权重体是状态，丢了就真没了；激活体是流量，有确定的生成规则（上一层的输出 ＋ 这一层的权重），丢了可以重跑一遍 forward 再造出来。这就是 activation checkpointing 全部的依据，也解释了它换来的为什么恰好是「算力换显存」——重算花的是算力，省下的是本来要留着等反向的那部分流量。

三 · 权重体在显存里是「×8 出现」的。bf16 参数每个 2 字节，但它带着同样大小的梯度和 6 倍大的优化器状态一起进显存，合计 16 B/参数。所以「参数量 × 2 字节」这个心算永远严重低估显存——它只算了那 16 分之 2。§12 里 7B 模型静态部分约 112 GB 的算法，就是这么来的。

四 · 通信搬的主要是激活体，不是权重体。除了 DP 的梯度规约和 ZeRO 的参数聚合，其余所有通信原语——PP 传层间激活、TP 传层内部分和、CP 传 KV、EP 传 token——搬的都是激活体。由此得到一条不太直观但很有用的推论：通信量主要随 batch 与 seq 增长，而不随参数量增长。换句话说，把模型改大不一定让通信变重，把 batch 或序列拉长却一定会。

两处边界

梯度与优化器状态严格说属于权重体。它们与参数同 shape、被同一组并行维度以同样方式切分，所以本文说「权重体」时默认含这三样；只在讨论字节数时才拆开算。

KV cache 是个混血，本文不展开。它的形状像激活体（随 b、s 增长），生命周期却像权重体（跨多步持续）——本质是被冻结成状态的激活体。这只在推理场景出现，本文是训练视角。

推论一：为什么恰好是四个乘数

ℓ、h、b、s 四根轴全网每一层都存在，各自能贡献一个独立乘数：

world_size = TP × CP × PP × DP

e 这根轴只在 MoE 层存在，非 MoE 层根本没有 expert 编号可切。一根时有时无的轴撑不起一个全局并行维度，所以 EP 只能借用已有平面上的卡重新分组。这才是「EP 不是第五个并行维度」的根本原因——「它是对 DP×TP 平面的重新解释」只是这个原因在旧版实现上的表现形式；新版换成了两套独立分解 + 中间重排，结论不变，见 §13 勘误 M。

两个都切 s。区别只在作用区间：CP 全程切，SP 只在 TP 区之外切。所以开启 SP 后，层边界处的序列维会被除两次：

逐个说清楚

DP 每张卡持有完整整网，各算各的数据，反向后 AllReduce 梯度。ZeRO / FSDP 是 DP 的变体——只是把参数 / 梯度 / 优化器状态的存储也切了，计算时仍临时聚合成完整整网。

PP 把整网按层切成若干 stage，每个 stage 内的层和算子都是完整的，stage 之间只传激活值，用 micro-batch 填流水线来掩盖气泡。

TP 一个 Linear 的权重被按列 / 行切开，单个 matmul 被分解到多卡上。它是唯一把算子的参数分片、需要改写算子本身的并行。

SP TP 只切了 matmul，LayerNorm / Dropout 这些区域的激活值仍是完整的；SP 把这些区域的激活值沿 seq 维也切开，顺势省下显存。所以 SP 与 TP 同域同大小，不占独立的并行维度。

CP 为长序列服务。逐 token 独立的算子（Linear、LayerNorm）天然不用通信；只有 Attention 需要看到全序列，所以通信集中在 attention 处。

EP 不同 expert 放不同卡，token 经 All-to-All 路由过去再回来。只作用于 MoE 层，非 MoE 层不受影响。每个 expert 在它那张卡上是完整的——算子没被改写，这一点与 TP 有本质区别。

嵌套顺序：由通信频率和通信量决定

TP / SP 通信最频繁（每层两次集合通信、量大），必须放最内层，绑在机内高带宽互联上。CP 次之，也尽量留在机内。PP 单次通信量最小（只传 stage 边界的激活），放外层、可以跨机。DP 每个 step 才通信一次且可与计算 overlap，放最外层。

勘误 A · EP 不是第五个并行维度

先前写作"总卡数 = TP × CP × PP × DP，EP 通常复用 DP 组的卡，或单独成维"，后半句不准确。EP 不是独立于这四个并行维度之外的额外乘数——它是对 MoE 层重新解释已有的 DP × TP 平面上的那批卡：非 MoE 层按 TP/DP 走，MoE 层把同一批卡重新分组成 EP 组。实现上通常要求 EP 组大小能整除对应平面的大小。所以世界大小仍是 TP × CP × PP × DP，EP 是这个网格上的一个视图，不是一条新的边。FIG 06 里选「EP 组」时高亮的正是同一 stage 的整个 TP×DP 平面，而不是新增一个轴。

勘误 B · "TP 是唯一切进算子内部的并行"说得太满

准确的说法是：TP 切分算子的参数（权重矩阵被拆开，matmul 本身被分解重写）；CP 切分算子的输入，但它同样要求 attention 算子改写——Ring Attention 需要 flash-attention 式的分块 online softmax 累加，逐块更新 running max 与 running sum，才能在只看到部分 KV 的情况下算出正确结果。所以"需要算子级改写"的有两个：TP 和 CP，只是改写的对象一个是参数、一个是规约方式。EP 和 PP 则完全不动算子。

06

映射：层与卡是多对多

三处说到"层"，指的都是整网定义里的同一种逻辑单元。层数永远是 N，不会因为并行策略而变多变少。变的不是层本身，是"层 → 卡上实例"的映射方式。

涉及的层单卡持有的映射性质层 → 卡能否独立算出这一层的正确输出
PP不同的层完整的层划分（沿深度切开一串层）N:1能
TP同一层层的分片分片（把层内的权重矩阵拆开）1:N不能（算出的是部分和）
DP同一层完整的层复制（同一层的多个副本）1:N能
EP同一层层内部分 expert（各自完整）划分（沿宽度分开放）1:N不能（token 需路由）

注意第 5 列：TP、DP、EP 三者的基数完全相同（都是 1:N），但映射性质三不相同。基数只回答「几对几」，不回答「是什么关系」——第 6 列那个判据才是区分它们的东西。这是 §01 那条提醒的具体落点。

这个判据和通信位置完全对应：PP 的通信在层的边界，DP 的在层之外（step 末），TP / EP 的在层的内部。所以"这一层在物理上不属于任何单卡"这句话，只对 TP 和 EP 成立，而且成立的理由不同。

勘误 C · EP 不该和 TP 并成"一层多卡"

先前把 TP 与 EP 一起归为"一层多卡的常态"，混了两件事。TP 是把单个权重矩阵拆开，算子本身被改写成分片，各卡算的是同一个 matmul 的不同部分。EP 是把层内并列的多个 expert 分开放，每个 expert 在它那张卡上是完整的，算子没被改写；层不完整是因为 expert 集合不全 + 需要路由。
从这个角度看，EP 更像 PP 的兄弟——都是把完整单元分开放，只是 PP 沿深度、EP 沿宽度；TP 才是那个真正把算子分片的。

为什么切分几乎总以层为单位 层 → stage N:1 stage → 卡 1:N

因为层间那条窄依赖是天然的低成本切口。PP 沿层边界切，卡间只需传一个激活值；如果切在层中间（比如 softmax 和后面那个 matmul 之间），要传的中间张量往往大一个数量级。

这带来一个实际约束：PP 的最小切分粒度就是层，层数除不尽 stage 数就会负载不均。

勘误 D · PP 负载不均不止"除不尽"

先前只提到"80 层切 6 个 stage 必然有卡多扛"。补充：即使整除也不均——第一个 stage 还要背 embedding，最后一个 stage 要背 lm_head 和 loss 计算（词表大时这部分显存和算力都很可观）。所以实践中常见的做法是首尾 stage 少分几层，做非均匀切分。把"层数 ÷ stage 数"当成唯一的均衡判据会漏掉这一项。

三者叠加时：第 37 层住在哪

第 37 层
  → PP: 落在 stage 2（哪几张卡）
    → TP: 在 stage 2 内被切成 8 份（这一层碎在 8 张卡上）

PP 决定层去哪几张卡，TP / EP 决定层在那几张卡里怎么碎，DP 决定这套安排复制几遍。层作为概念自始至终没变，变的只是它被映射到硬件上的方式——这正是讨论并行时层始终是最省力参照单位的原因。

07

逻辑侧 ↔ 物理侧：两条链不是逐级对齐的

逻辑侧五级、物理侧五级，看起来对称，但它们的对应关系是斜的。最关键的一点：所有并行切分都收在物理侧的同一级上。

上下两级都不参与切分

  • 集群、机：不参与切分，只决定拓扑与带宽。机的存在只影响「TP 域必须放机内、PP 域可以跨机」这类约束，不改变切法。
  • 计算单元、片上 buffer：与并行完全无关。tiling 也是切，但不跨卡、不通信、不改语义。

为什么偏偏是卡：一个判据，三个身份

「都落在卡上」不是约定俗成，是可以推出来的。先把「并行切分」这个词说严：

判据

一刀算不算并行切分，看它是否改变状态的归属——切开之后，索引空间的不同子块分属不同的持有者，且按 §02 的通则，切口处必须插入通信算子来补齐。这句话预设了持有者必须具备三种能力：私有地址空间（归属才有边界）、通信端点（补齐才有收发方）、独立执行流（分片才能同时被算）。

拿这三项把物理侧五级逐个过一遍：

物理级私有地址空间通信端点独立执行流所以它是
集群✗ 只是全部卡显存的并集✗ 是端点的集合，不是端点✗拓扑
机✗ 没有「机显存」——机内没有任何一个张量属于机而不属于某张卡✗✗带宽边界
卡✓ 显存✓ rank✓ 流唯一三项全齐 → 落点
计算单元✗ 所有单元读写同一块 HBM✗并发，但由同一调度器统一喂执行
片上 buffer✗ 装的是 HBM 数据的临时副本，不拥有数据✗✗执行

只有卡三项全齐。上两级只有聚合、没有归属——所以它们出现在约束里（「TP 必须机内」是带宽约束），从不出现在切法里；下两级只有共享、没有边界——计算单元之间交换数据靠写回同一块 HBM 再读出，不需要也不存在通信算子，所以 tiling 分的是工作在时间上的排布，不是状态在空间上的归属。这正是上面那句「不跨卡、不通信、不改语义」的由来。

把这说到底就是一句话：地址空间的边界在哪里，并行的落点就在哪里。并行切分本质是「把索引空间的子块分派给不同的地址空间」（§10：rank 元组是地址）；物理五级里，地址空间的粒度恰好就是卡——往上没有更大的统一地址空间（peer 访问是搬运手段，框架的归属记账仍以卡为界），往下没有更小的独立地址空间。

还可以换一个函数视角：整个并行配置就是一个映射 (ℓ, e, b, s, h) → (pp, ep, dp, cp, tp) → global_rank → 卡，值域是卡的集合。集群与机从不出现在这个函数里，只影响「哪个函数是好主意」（§11 的 order 与整除约束）；计算单元与 buffer 只在函数求值之后出现——卡拿到自己那块之后怎么算，已经与「分给谁」无关。卡是「分派」与「执行」的交接面：以上决定哪张卡算，以下决定这张卡怎么算。

与 §02 的对偶

§02 说两条链在 kernel 处汇合——那是逻辑侧的唯一交点；本节说四条并行映射在卡处汇合——这是物理侧的唯一落点。两者是同一事实的两面：kernel 按定义是一张卡上的一次执行（「不可再跨卡的那一级」），卡按定义是 kernel 排队执行的地方。TP 把归属边界推到最深（kernel）时落点仍是卡——因为「归属」这个概念本身就是以卡为单位定义的。

压力测试：四个像反例的例子
  • MIG 把一张卡切成几份——但每个实例拿到的是独立的显存切片 ＋ 独立设备号，可各绑一个 rank：想在卡以下参与并行，必须先把那个单元改造成卡等价物。这是判据的正面印证，不是反例。
  • 超节点把高带宽域扩出单机——「TP 必须机内」松弛为「TP 必须在高带宽域内」。变的是上两级的形状（约束），不变的是落点（仍是卡）。
  • ZeRO / FSDP 切的不是那四根轴（切的是 DP 组内的冗余副本），但分片单位仍然是 rank，即仍然是卡。
  • offload 用了主机内存——机确实有自己的 DRAM，但它在切分语义里不是持有者：offload 只是某个 rank 把自己名下的状态暂存到墙外仓库，归属记账没有离开 rank。
口径核对

与实现对得上：Megatron / torch.distributed 里 world_size ＝ 进程数（标准排布一进程绑一卡，§10），所有并行组（TP / CP / PP / DP / EP 组）的成员都是 global rank 的列表；initialize_model_parallel 的输入只有各维大小与 order 字符串——「机」这个概念在切分语义里根本没有入口，它只通过两条侧门进入：rank 排布约定（stride 1 的组落机内，§11）和配置约束（TP ≤ 机内卡数）。

所以「整网怎么在卡上切分」这个问题，答案的全部信息都在卡这一级。这也解释了为什么单卡视角（显存里放了什么 / 流上排了什么）能撑起那么多诊断——并行的一切后果都在那里落地。

追踪一个算子：从整网到单卡

整网    权重 [8192, 32768]    激活值 [256, 8192, 8192]

从这段能直接读出三件事

  • 对单个算子实例而言，PP 是筛子，其余三个是除号。PP 决定这一层在不在这张卡上（有 / 没有），TP / CP / DP 决定在的话剩多大。注意这个说法只在「盯着一个算子」时成立——对整张卡而言，PP 同时也是层数的除号（L/PP）。
  • 只有 TP 那一行的权重变了。CP 和 DP 那两行权重原封不动——这就是它们「复制整网、只切输入」的字面含义。
  • 逻辑索引 → 卡坐标是纯算术。给定 (ℓ, b, s, h) 落在哪个区间，就唯一确定 (pp, dp, cp, tp)，再由排布约定算出 global_rank；反过来给 rank 也能反解出它负责哪一段索引。

四刀有没有先后：地址的四个数位，不是四道工序

FIG 10 从上到下一刀接一刀，容易读成流水工序。其实那是叙述顺序：四刀作用在四根互不相干的轴上（层号、隐藏维、token 位置、样本号，§03），构成笛卡尔积，先切哪刀得到的分块完全相同（§11 层面一，三处例外也在那里）。更准确的读法是：卡坐标 (pp, dp, cp, tp) 是一个四位数的门牌号，四刀是这个门牌号的四个数位——数位之间没有「先写哪一位」的时间概念。图里把 PP 放在第一刀有个真实的理由，但那不是时间，是求值：PP 是筛子、其余是除号，筛掉了，除号无意义——这只是「读这张图」的顺序，不是「切」的顺序。

那有没有什么顺序是真实存在、并且被持续保留的？有三个，各在不同层面，都不是「切的先后」：

真实存在的顺序它是什么保留在哪里 · 保留多久
切分结果谁拿哪块——卡的四元坐标与所有通信组initialize_model_parallel 时一次建成，整个 run 冻结不变。权重分片建模时物化一次、跨 step 常驻；激活分片每 step 生灭，但每次按同一条规则切

MoE 的 token 路由：激活体在 e 轴上的归属逐 token 由 router 现场决定，是全文唯一「切分结果不静态」的地方——这也是 EP 那一行时间线负载不均的根源（§12）。注意只有激活侧动态；权重侧 expert 放在哪张卡，仍然是初始化时定死的。

所以对「切分有顺序吗、顺序保留吗」的完整回答是两句话：「切」没有顺序——四刀是同时成立的笛卡尔积；「切出的结果与编址方式」有顺序且被持续保留——冻结在通信组与 rank 编码里，直到 run 结束。

对 viewer 的推论

这套映射是可逆的，意味着界面可以做双向：点一张卡，高亮它负责的索引区间；点整网上的某一层某个权重块，高亮持有它的那批卡。目前 axis= 这类参数只支持了前一个方向。

诊断时能不能绕开两个体，合起来看

能，而且应该——但只在入口。这正是「一切落在卡上」的直接应用：在卡这一级，权重体与激活体是同一种东西——显存里的字节 ＋ 带除号的 shape，且都由同一个卡坐标唯一决定（§10：rank 元组是地址）。所以诊断的第一步天然不分体：

症状合着看的入口用到哪个统一柄
OOM容器只认总和——FIG 11 里四段堆的是同一根柱，溢出不问出身容器总量
shape / 数值对不上先对除号：该卡的每个 shape 是否被正确的维度除小（§03 推论三）shape 上的除号
hang / 等待看通信域与坐标，与体无关（§12 的「嫌疑人」判别法）卡坐标

但拆是躲不掉的第二步，因为处方跟着轴走、轴属于体（§03）：两个体的增长规律不同（权重体只随模型结构，激活体随 batch × seq）、旋钮不同（权重体超 → TP / PP / ZeRO；激活体超 → CP / MBS / 重计算）。合着看只能说「满了」，拆开才知道拧哪个。

就算不拆帐，时间轴也会替你拆

「状态 vs 流量」（§03）在监控曲线上有直接投影：显存占用一开始就高、全程平直——权重体问题，它在第一个 token 之前就已分配；随层数爬升、随 step 锯齿——激活体问题，它逐层堆积、每 step 生灭。两个体的生命周期差异大到曲线形状本身就能分体，不需要先拆帐。

结论：两个体不是可以绕开的实现细节，而是诊断树的第一个分叉。定位流程天然是「合进、分出」：症状层合着看（卡坐标 ＋ 容器总量 ＋ 时间线），归因层拆开走（哪个体 → 哪根轴 → 哪个并行维 → 哪个旋钮）。

08

卡作为容器：谁能减什么

全局只有两个被切的对象：权重体和激活体。四个并行维度是落在它们身上的四刀——两刀切权重，两刀切激活。卡是接住碎块的容器，容器满了就是 OOM。

调大它权重 · 梯度 · 优化器状态激活值为什么
TP全减减（开 SP 时）切的是权重体的 h 轴，参数量真的少了
PP全减减切的是权重体的 ℓ 轴，这张卡少背几层
CP不变减只切激活体的 s 轴，权重一份不少
DP不变不变只切全局 batch，单卡的 micro-batch 没变小
DP 那一行值得单独说

把 DP 从 2 调到 8，卡数从 128 涨到 512，容器里一点变化都没有——这是容器视角最反直觉、也最有用的一条。DP 增加的是吞吐和总卡数，不是单卡的余量。所以「显存不够就加卡」这句话，只有在加的是 TP 或 PP 时才成立；加 DP 是买吞吐，不是买余量。

例外是 ZeRO / FSDP：它们把优化器状态（乃至梯度、参数）沿 DP 域切开，这时 DP 才开始减容器里的东西。但那是给 DP 打的补丁，不是 DP 本身的性质。

09

通信：切口处插入的算子

并行切分之后，框架会在切口处往整网里插入通信原语。关键认知：通信算子对卡来说也是算子，也排在同一条流上占时间。

AllReduce（集合通信） N:1 → 1:N

域内每张卡都持有一份同 shape 的数据，做一次全局规约（通常是求和），结束后每张卡都拿到相同的完整结果。两个高频场景：DP 的梯度同步（每 step 一次）；TP 的层内激活值求和（每层两次，因为权重被切开后各卡算出的是部分和，必须加起来才等于原 matmul 的结果）。

Ring 实现下每卡的通信量约为 2(N−1)/N × S，S 是数据量——注意它不随卡数线性增长，这是 Ring 算法的核心价值。

All-to-All（集合通信） N:N 各不相同

每张卡把自己的数据按目标 rank 切成 N 份，各发各的、各收各的——本质是一次分布式转置，每张卡收到的内容都不同（这是它和 AllReduce 最大的区别）。

最典型的用途是 EP：token 被 router 判定该去哪个 expert，dispatch 一次 All-to-All 送过去，算完 combine 再一次送回来。所以一个 MoE 层前向就有两次，反向同样两次，是 EP 的主要开销来源。但它不为 EP 专有——Ulysses 语义的 CP 同样以 All-to-All 为核心原语（把 seq 维切分转成 head 维切分）。

P2P / Send-Recv（点对点，不是集合通信） 1:1

只有两张卡参与，一发一收。PP 专用：stage N 算完把边界激活发给 stage N+1，反向时梯度沿反方向传回。

勘误 E · "PP 通信量最小"要加限定

准确说是单次通信量最小（一个 [b, s, h] 激活张量，不是整份权重）。但通信次数是 micro-batch 数 × stage 边界数，micro-batch 开得多时总量并不小。"PP 可以跨机"成立的理由是单次通信量小、且能与计算 overlap，不是总量小。

AllReduce 与 SP 的关系：两处描述并不矛盾

这里有一个看起来打架、实则不冲突的点，值得写清楚：

  • Ring 实现下 AllReduce = ReduceScatter → AllGather（先规约散开，再聚齐）。
  • Megatron SP 的前向里，进入 TP 区用 AllGather（把 seq 切分的激活值聚成完整），离开 TP 区用 ReduceScatter（把部分和规约并沿 seq 重新切开）——顺序是反的。

两者不矛盾，因为站的位置不同：前者是拆解一次 AllReduce 的内部实现，后者是描述一层前后两个通信算子各用什么。SP 的实际效果是把原本一次完整 AllReduce 的两半拆到层的两端，中间那段激活值顺势保持 seq 切分状态。通信总量与纯 TP 相同，省下的是激活值显存。

解绑：切分维度并不决定通信原语

先承认一个表述问题

本文此前（包括 FIG 06 的交互按钮、FIG 12 的图例、以及各处「TP → AllReduce、PP → P2P、EP → All-to-All」的写法）把并行维度和通信原语讲成了一一对应。这是典型实现的对应，不是本质对应。§01 的基数表里写的 并行策略 → 原语 N:M 才是对的，正文与图没跟上。这一小节补齐。

真正决定原语的，是切口两侧的数学关系

并行的名字（TP / PP / DP / EP / CP）描述的是切哪一维；而通信原语由切开之后各卡手里的东西和完整结果之间差了什么决定。这是两件事：

切口性质各卡手里是什么需要的动作可选原语
切在求和 / 归约维部分和加起来AllReduce、ReduceScatter（+ 后续 AllGather）
切在拼接维完整张量的一片拼齐AllGather、Broadcast
切在归属维归属错位的数据重新分配All-to-All
只有前后依赖上一段的输出递给下一个P2P Send / Recv

所以链条是两层，不是一层：

并行策略  →  切口的数学关系  →  可选原语集合  →  实现按通信量 / 显存 / 拓扑选一个
   (名字)        (真正的约束)        (多选一)              (工程权衡)

后两步是多选一，不是唯一确定。这就是 N:M 的来源。

反过来同样成立：一个原语服务多个维度。All-to-All 既是 EP 的核心，也是 Ulysses CP 的核心；AllReduce 既服务 DP 也服务 TP，而这两者的相似之处仅在于「切的都是求和维」，与它们本身像不像毫无关系。所以在 profiling 里看到 All-to-All 就断定「这是 MoE」，是把 N:M 当成了 1:1。

那最初为什么会这么讲

因为用典型实现建立直觉最省力，而 Megatron-LM 的默认配置事实上就是那一套对应。作为入门脚手架没问题，但把脚手架讲成结构就越界了。这个越界在治理场景里有实际代价：一旦用户的性能问题来自非标准实现，按并行的名字反查原语会直接把定位方向带偏。

编号：卡与 rank 不是一回事

物理上通常一张卡对应一个 rank，但一张卡同时持有多个 rank 编号。All-to-All 里说的"目标 rank"，指的是通信域内的编号，不是全局卡号。

rank 是"在某个通信域里的编号"，不是卡的身份证 卡 → rank 编号 1:N

严格定义：rank 是一个进程在某个通信域（communicator / process group）内的序号，范围 0…N−1。训练默认配置是一进程绑一卡，所以 global rank ↔ 卡确实是 1:1，日常混着说没问题。

混淆的根源正是基数：卡 → global_rank 是 1:1，但卡 → rank 编号总数是 1:N。前者让人以为「卡就是 rank」，后者才是实际情况——一张卡同时挂在多个通信域上，每个域给它一个不同的号。

但并行切分会同时建立好几个通信域，每个域各自从 0 开始重新编号。于是同一张卡会有一整组坐标：

global_rank = 21   ← 全局唯一，对应物理卡
  ├ tp_rank = 1    ← 在它的 TP 组（4 卡）里排第 1
  ├ ep_rank = 5    ← 在它的 EP 组（8 卡）里排第 5
  ├ pp_rank = 2    ← 它属于第 2 个 stage
  └ dp_rank = 0    ← 它是第 0 个整网副本

具体算一遍：32 卡、TP=4、EP=8、排布按 [ep][tp]（TP 在最内层，且此例简化为 PP=DP=1）。

global_rank = 21
  ep_rank = 21 // 4 = 5
  tp_rank = 21 %  4 = 1

卡 21 发出的第 3 份数据 → 给 ep_rank = 3 的那张卡
  它的 global_rank = 4 × 3 + 1 = 13

所以 All-to-All 里的"目标 rank"是 EP 域内 0–7 那个编号，"切成 N 份"的 N = 8（EP 组大小），不是 32。

rank 与图 / 权重体 / 激活体：rank 是地址

把 §03 的三样东西接到这里，rank 的作用就一句话：rank 元组是这张卡在五维索引空间里的地址，它唯一决定这张卡从每根轴上取走哪一片。

轴属于切它的并行对应 rank这个 rank 决定
ℓ 层号权重体PPpp_rank这张卡持有哪几层
h 隐藏维权重体TPtp_rank持有权重矩阵的哪一列 / 行
e expert 号权重体EPep_rank持有哪几个 expert
b 样本号激活体DPdp_rank处理哪一段 batch

给定坐标，每根轴上的区间就是纯算术（以最朴素的均匀切法为例）：

层     ℓ ∈ [pp_rank · L/PP,  (pp_rank+1) · L/PP)
隐藏维  h ∈ [tp_rank · H/TP,  (tp_rank+1) · H/TP)
expert e ∈ [ep_rank · E/EP,  (ep_rank+1) · E/EP)
样本    b ∈ [dp_rank · B/DP,  (dp_rank+1) · B/DP)
序列    s ∈ [cp_rank · S/CP,  (cp_rank+1) · S/CP)   ← zigzag 切法下是不相邻的两段

三样东西各自被哪些 rank 决定

pp_rank 与 tp_rank 同时出现在两边——因为 ℓ 和 h 是共享轴（§03）。ep_rank 只进权重体的地址，dp_rank / cp_rank 只进激活体的地址。这张表不是新知识，它就是「共享轴」那条结论在编号上的投影。

由此得到一个判据：两张卡「一样不一样」

两张卡只有这一位不同权重体激活体
dp_rank完全相同（副本）不同——不同的样本
cp_rank完全相同（副本）不同——不同的序列段
tp_rank同一个矩阵的不同分片TP 区内是同一份；开 SP 后在 TP 区外是不同分片

注意头两行完全一致：DP 与 CP 在权重体这一侧的行为一模一样，都是完整副本。这是 §06「CP 就是会漏的 DP」最硬的一条证据——它们的差别只体现在激活体那一列，以及那个唯一的漏点（attention）。

rank 是地址，不是身份

rank 本身不携带任何「这张卡与众不同」的含义，它纯粹是个索引。所有卡跑的是同一份程序，只是各自按自己的 rank 去取对应的那一片——这就是 SPMD（single program, multiple data）能够成立的全部条件：图不被切（§03）＋ rank 是纯地址（本节）。少了任何一条，各卡就得跑不同的代码。

还有一层双重身份值得留意：域内 rank 既是「取哪一片」的索引，也是「跟谁通信」的收发地址。框架保证这两者一致；order 字符串（§11）改变的只是这些逻辑组到物理卡的映射，不改变索引与通信对象的对应关系。

为什么必须说 rank 而不能说卡

因为通信原语永远发生在某一个通信域内部，它对全局卡号一无所知。集合通信库的 API 拿到的就是域内 rank。同一张卡在 TP 域里是 rank 1、在 EP 域里是 rank 5——说"发给卡 13"没有歧义但没有意义，底层要的是"发给本域的 rank 3"。

1:1 也不是铁律 ※ 随部署方式变

  • 一进程多卡（一个 rank 管多张卡，少见）
  • 一卡多进程（推理多实例、MPS）
  • CPU 进程也占 rank（某些混合部署）

另外还有个容易混的 local_rank——那是机内编号（0–7），用来 set_device 绑卡的，和通信域 rank 是两回事。

切分的先后顺序：四种不同的「先后」

「各种切分有没有先后顺序」这个问题，问的其实是四件不同的事。分开看，答案分别是：基本没有、有且是性能关键、有且形成依赖链、只有一个维度有。混在一起问，就会得到自相矛盾的答案。

层面有没有先后结论
数学 · 可交换性基本没有切的是相互正交的轴（§03 的五根轴），构成笛卡尔积，与应用顺序无关。三处例外见下
rank 排布有，且是性能关键order 字符串决定每个通信组落在机内还是跨机
配置决策有，整除约束形成依赖链DP 是残差维，永远最后由剩余卡数算出
执行时序只有 PP 有PP 轴上是严格因果次序，其余维度同刻并行（§12）

一 · 数学层面：基本可交换，但有三处例外

五根轴彼此独立，所以「先按 batch 分再按层分」与反过来得到的分组集合完全一样。抽象结构与应用顺序无关——这是「切分对称」这个直觉的合理内核。但有三处真实的依附与不可交换：

  • SP 必须依附 TP，不能独立存在。它切的正是 TP 切不到的那部分激活值（LayerNorm / Dropout 区域）的 seq 维，且严格复用 TP 的通信域。Megatron 里 --sequence-parallel 要求 tensor_model_parallel_size > 1。这印证了 §00 表 A 与 §03 的判断。
  • TP 与 EP 在 MoE 层是两套不同的分解。attention 走 TP×CP×DP×PP，expert 走 ETP×EP×EDP×PP，两套 mesh 形状不同，边界上必须做 token permutation + All-to-All-V 重排，算完再逆向送回。Megatron-Core 称之为 MoE Parallel Folding。「先按 expert 分再切权重」与「先切权重再分 expert」对应完全不同的通信拓扑——这里的先后是实质性的。
  • EP 与 CP 不能进同一个 RankGenerator。源码里有断言把二者隔开。注意别误读：这不是说 EP 和 CP 不能同时启用，而是它们分属两个不同的 RankGenerator 实例——attention 部分才有 seq 维（CP），expert 部分 token 已被打散，用 DP 取代 CP。

二 · rank 排布：order 字符串决定物理落位

§04 说过嵌套顺序是「TP 最内、DP/PP 最外」，但那是约定的说法。真正的机制在 Megatron 的 RankGenerator 里：

megatron/core/parallel_state.py
initialize_model_parallel(..., order: str = "tp-cp-ep-dp-pp")

# RankGenerator 用前缀积算 stride
prefix_product([tp, cp, ep, dp, pp]) → [1, tp, tp·cp, tp·cp·ep, ...]
                                        ↑
                        order 最左那个维度 stride = 1

global_rank = tp_rank + dp_rank·tp_size + pp_rank·tp_size·dp_size

最左 = stride 1 = 组内 global_rank 连续 = 落在同一台机内。这就是 TP 必须放最左的全部理由——它每层两次集合通信，频率最高，必须走机内高带宽互联；DP 每 step 才一次，放最右、成员跨机也无妨。

改 order 不改变抽象分组，只改变物理落位。同样是「谁和谁在一个 TP 组」，换个顺序字符串，这些通信就从机内挪到了跨机。

源码里一处真实的自相矛盾

initialize_model_parallel 的函数签名默认值是 order="tp-cp-ep-dp-pp"，但同一文件的 docstring 仍写着过时的 default=tp-dp-pp，并声称只支持 tp-dp-pp 和 tp-pp-dp。早期版本（支持 CP / EP 之前）确实是后者，加入 CP 和 EP 后签名更新了、注释没跟上。以签名为准。

有 MoE 时会建两个独立的 RankGenerator：一个给 attention（带 cp、ep=1），一个给 expert（带 ep、cp=1）。两者的 PP 组必须一致。这也让 §04 勘误 A 的说法需要更新——见下方勘误 M。

三 · 配置决策：整除约束形成依赖链

约束公式说明
注意力头num_attention_heads % TP == 0GQA / MQA 时还要 num_query_groups % TP == 0；不整除需 pad dummy head，会浪费算力
专家数num_experts % EP == 0源码有对应断言
层数num_layers % PP == 0首尾 stage 还要背 embedding 与 lm_head，可用 decoder_first/last_pipeline_num_layers 做非均匀切分（印证 §06 勘误 D）

一个广泛流传的错误算法

估算 MoE 配置的最小卡数时，不能用 PP · TP · CP · EP · ETP 连乘——这会严重超配。正确的是：

最小卡数 = PP × max(TP·CP, EP·ETP)

因为 dense path 用 TP·CP mesh、MoE path 用 EP·ETP mesh，二者在每个 PP stage 内共享同一批卡（取 max，不相乘），只有 PP stage 之间才是相乘。NVIDIA 的调优文档专门把连乘式标为错误，并指出它出现在很多 README 和排期表里。

由此得到的五步决策顺序

  1. 先定 TP——受两个硬约束：head 数整除，且 TP ≤ 单节点高带宽域卡数（典型 8）。若此时单卡装得下，就停在 TP + DP，不引入 PP。
  2. 再定 PP——仅当 TP 已到机内上限仍 OOM 时引入。
  3. 长序列加 CP——经验法则：TP 随 KV head 数扩，CP 随序列长度扩。
  4. MoE 加 EP / ETP——EP 尽量留机内；ETP 通常设 1，避免 MLP GEMM 的 TP 通信开销。
  5. DP 最后自动定——它是剩余卡数，不是一个可选项。

四 · 执行时序：只有 PP 有严格因果

这一层的完整展开在 §12，这里只补两条印证：

  • 各并行的通信按发生频率排序（TP 层内 → CP/SP 层内 → EP 的 MoE 层 → PP 的 stage 边界 → DP 的 step 末），恰好是 order 字符串从左到右的镜像。嵌套顺序、rank 排布、通信频率三者是同一件事的三种写法。
  • CP 的时序完全取决于实现：Ring Attention 的 KV 沿环轮转，CP 轴上有明确的循环时序（第 i 轮才拿到第 i 块 KV）；Ulysses 用两次 All-to-All 把「seq 切分」换成「head 切分」，轴上没有时序。这正是 §09 那条「维度不决定原语」的又一佐证。
与本文既有结论的关系

印证了：world_size = TP × CP × PP × DP（§04）、EP 不是独立乘数维（§04 勘误 A）、SP 与 TP 同域同大小（§00、§03）、维度与原语是 N:M（§09 解绑）、PP 负载不均不止「除不尽」（§06 勘误 D）、PP 是唯一有因果次序的维度（§12）。

需要更新的：见下方勘误 M。

勘误 M · EP 的机制说法需要按版本区分

§04 勘误 A 说 EP 是「对 DP×TP 平面的重新解释」。这在经典 EP（较早的 Megatron-Core）下成立，但在采用 MoE Parallel Folding 的新版里应更新为：attention 与 expert 各有一套独立的 RankGenerator 与并行 mesh，二者在同一 PP stage 上共享 GPU，靠 token 重排衔接。

结论方向不变——EP 仍然不是 world_size 公式里的第五个乘数——但机制描述从「重新分组」变成了「两套独立分解 + 中间重排」。而且这条约束本身随版本变动很大（经典 EP 要求 EP = DP·TP，ETP 模式要求 EP = DP，Folding 后完全解耦），引用时必须核对 Megatron-Core 版本号。

本节的可靠性边界

参数名、默认值与公式来自 Megatron-LM 源码与 NVIDIA 官方文档，属一手来源。但三点需要留意：其一，EP 相关约束在不同 Megatron-Core 版本间语义差异极大，务必核对版本；其二，「最左 = 机内」成立的前提是启动脚本把 rank 正确映射到物理卡，若 NUMA / 拓扑错配，TP 仍可能跨机。

运行时：单卡的空间与时间

一张卡本质上是一块 HBM + 一组计算单元 + 若干条执行流。它不认识"整网"，只认识两件事：显存里放着什么，和流上排着什么。

空间：HBM 里放了什么 卡 → HBM 1:1

占用项性质量级
权重静态，训练全程常驻bf16：2 字节 / 参数
梯度反向产生与权重同量级
优化器状态混合精度下常是大头Adam：fp32 master weight 4 + momentum 4 + variance 4 ≈ 12 字节 / 参数
激活值动态，前向逐层堆积、反向逐层释放≈ 层数 × 单层激活值量，随 batch × seq × hidden 增长
通信 buffer · workspace · 内存碎片随并行配置与算子实现变化常被低估

能不能单卡放下整网，取决于这五项之和——不是取决于整网有多少参数。算一遍 7B 全量训练：

权重 (bf16)      7B × 2  =  14 GB
梯度            7B × 2  =  14 GB
优化器状态       7B × 12 =  84 GB
                        ─────────
静态部分小计            ≈ 112 GB   ← 激活还没算

所以 64 GB 单卡训不动 7B，不是因为 14 GB 的权重放不下，而是优化器状态就是权重的 6 倍。激活值显存是按层累积的——前向走到第 k 层时前 k 层的激活值都得留着等反向用，这也是重计算（activation checkpointing）以层为粒度做的原因：丢掉中间激活，反向时重跑这一层的前向，用算力换显存。

时间：流上排了什么 流 → kernel 1:N

整网是并行的（有分支），但一张卡的执行流是串行的。框架把这张图按拓扑序摊平成一个 kernel 队列，卡上一次执行一个（或少数几个并发）算子：读输入张量 → 算 → 写输出张量 → 下一个。

所谓"整网在卡上运行"，物理真相就是一条几千到几万个 kernel 的执行序列被反复刷过去，中间穿插内存分配 / 释放。这是为什么 profiling 出来是一条时间线，而不是整网那样的一张图。

层在这条时间线上表现为周期性重复的波形——那段肉眼可见的重复 pattern 就是层。这也是性能分析的抓手：拿准一层的耗时乘以层数就是整网基线，某层异常凸起立刻可见。

而且一张卡上不止一条流 卡 → 流 1:N

至少是「计算流 + 通信流」双流：把 AllReduce 丢到独立流上，让它和后续算子的计算重叠，这就是 overlap。所以严格说，是 N 张卡 × 每卡若干条流，靠 event 做流间同步。

算子的两类瓶颈

  • 计算密集型（大 MatMul）：吃满矩阵计算单元，算力是瓶颈。
  • 访存密集型（LayerNorm、Add、激活函数、Softmax）：算得很快但反复读写 HBM，带宽是瓶颈，计算单元大量空转。

算子融合的价值就在这里——把连续的访存密集型算子合成一个 kernel，中间结果留在片上不落 HBM。

N 条时间线：卡与卡之间没有全局时钟 卡 → 时间线 1:1 线间 N:M

每张卡一条独立的执行流，各跑各的。它们之间唯一的耦合是通信算子：谁先到谁就等着，直到域内所有 rank 都到齐。所以"整网在跑"这件事，物理上是 N 条各自推进、被通信算子反复钉在一起的时间线。

维度时间线差异成因
TP几乎锁步，偏差以微秒计每层两次 AllReduce，且各卡算子完全对称（切的是权重，shape 一致）
DP同构但异步跑相同的整网、数据不同，中途互不干涉，直到 step 末一次梯度 AllReduce 才对齐；快慢来自变长序列、padding 比例
PP差异最大，阶梯状错开stage 0 跑 micro-batch 1 的前向时 stage 3 还在空转等激活；1F1B 下每个 stage 的 F/B 交错节奏都不同
EP节奏相同但负载不均router 把 token 分给各 expert，热门 expert 所在的卡多算好几倍；靠 capacity factor 与负载均衡 loss 压制
CP因果掩码天然不均持有靠后 seq 分片的 rank，attention 要看的历史更长；实现上用 zigzag / striped 分配把长短片段交叉配对
高频诊断陷阱

profiling 里看到某张卡的 AllReduce 耗时 40 ms，绝大多数情况不是链路慢，是这张卡先到了、在等别人。集合通信的耗时天然包含域内最慢者的等待。真正该看的是：

  • 通信耗时在各 rank 上不均——某几张特别短、其余特别长，说明短的那几张是慢的源头（它们晚到，几乎不用等）
  • 通信耗时普遍偏长且均匀——才更可能是带宽或拓扑问题

这个归因方向是反直觉的：等待时间长的卡是"受害者"，等待时间短的卡才是"嫌疑人"。工具如果只呈现单卡时间线，用户几乎必然会归错因；只有把多 rank 的时间轴叠在同一坐标上、并标出通信算子的进入 / 退出时刻，慢的那一张才会自己浮出来。

时间是第几维？

短答：时间不是那四个切分维之一，但 PP 已经是时间的空间化。

world_size = TP × CP × PP × DP 里的四个维度全是空间维——它们划分的是卡的集合，每张卡拿到一个四元坐标。时间不在其中。但这四个维度里，PP 是特殊的：

维度轴上有序吗表现
TP无序，完全对称tp_rank 0 和 3 在同一时刻做同样的事，锁步；交换编号不改变任何东西
DP无序，完全对称副本之间互不干涉，step 末才对齐
CP取决于实现Ring Attention：KV 沿环轮转，有循环时序；Ulysses：一次 All-to-All，无时序
PP严格有序、有方向对同一个 micro-batch，stage k 必须先于 k+1 —— 这就是时间

PP 的一切特征其实都是时间特征：气泡（纯时间产物——其他三个维度里根本没有「气泡」这个概念）、需要 micro-batch 去填（对时间的再细分）、通信是有方向的 P2P 而不是对称的 AllReduce、多 rank 时间线呈阶梯状。

pp_rank 本质是一个被空间化了的时间下标。这也是为什么它同时出现在 FIG 06（网格）和 FIG 15（时间线）里——它是唯一同时属于两边的轴。

不同 stage 是并列的，还是一个跑完再跑下一个？

都不是——是错开重叠。这个问题要分成两句话答，因为答案取决于问的是「同一个 micro-batch」还是「不同的 micro-batch」：

  • 对同一个 micro-batch：严格串行。它必须依次流过 stage 0 → 1 → 2，这是数据依赖强加的因果次序，无法并行。FIG 16 右图那条深色箭头链画的正是它——向右上走，每上一级都往后挪一格时间。
  • 对不同的 micro-batch：并行。micro-batch 1 在 stage 1 上算的同时，micro-batch 2 已经在 stage 0 上开工了。图上三行在横轴上互相重叠，重叠的部分就是这种并行。

所以「流水线」这个名字是准确的。类比装配线：一件产品必须依次经过每个工位（串行），但不同产品可以同时占着不同工位（并行）。PP 的全部效率来源，就是用后者去填前者留下的空。

阶段发生什么与气泡的关系
warmup 预热stage k 要等 k 个时间单位才拿到第一个 micro-batch，此前一直空转气泡的前半——图上左下角那片空白
steady 稳态所有 stage 同时都有活干，并行度最高无气泡。1F1B 调度的全部目的就是让这段尽量长
cooldown 排空最后几个 micro-batch 陆续走完，stage 0 先空下来气泡的后半——图上右上角那片空白
气泡占比 ≈ (PP−1) / GA

warmup 与 cooldown 合计约 PP−1 个时间单位，稳态约 GA 个，所以气泡占比大致是 (PP−1)/GA。这就是 §03 那条「GA ≥ PP」的量化版：GA 越大气泡越小。

但 GA 不能无限加——它受 GBS = MBS × GA × DP 约束，加 GA 要么抬高 GBS（影响收敛与学习率），要么压低 MBS（可能让单卡算不满）。这三者是一组联动的旋钮，不能只看其中一个。

那 stage 与 stage 之间到底是什么关系

一句话：stage 之间是「链」，不是「组」。TP 组、DP 组都是对称集合——组内成员可以互换编号而不改变任何东西；PP 是一条有向链，成员不可互换。这也是它用 P2P 而非集合通信的根本原因。展开看有七层：

关系维度stage 之间是什么关系
数据依赖单向链：stage k 的输出激活值就是 k+1 的输入；反向时梯度沿同一条链倒流。每个 stage 只有一个前驱、一个后继
通信只在相邻两个之间有 P2P。非相邻 stage 之间没有直接通信——stage 0 和 stage 3 不做任何集合操作（例外见下）
时间错开重叠。对同一 micro-batch 严格串行，对不同 micro-batch 并行
权重完全不同的层，零重叠。对比 DP（逐字节相同）与 TP（同一矩阵的不同分片），这是三种截然不同的关系（§10）
负载名义均分 L/PP 层，实际首尾偏重（§06 勘误 D）。关键是最慢的那个 stage 决定整条流水线的节拍——木桶效应
显存严重不对称，见下方专述
编号pp_rank 的大小有意义（0 在前、大的在后）；而 tp_rank、dp_rank 只是标签，换了编号什么都不变（§12 有序维 vs 对称维）
最容易被忽略的一层：靠前的 stage 显存压力更大

直觉上每个 stage 分同样多层、显存应该差不多。实际上在 1F1B 调度下，靠前的 stage 要同时压着更多在途 micro-batch 的激活值。

原因是因果次序：stage 0 前向完第 1 个 micro-batch 后不能立刻做它的反向——得等它一路走到最后一个 stage 再一路退回来。这段等待里 stage 0 已经又前向了好几个 micro-batch，而每一个的激活值都得留着。稳态下 stage k 手里压着约 PP − k 份：

stage 0     压 PP 份 micro-batch 的激活值   ← 显存压力最大
stage 1     压 PP−1 份
   ⋮
stage PP−1  压 1 份                          ← 最轻松

所以 PP 下的 OOM 几乎总是先发生在 stage 0，而它恰好还额外背着 embedding。首 stage 少分几层的非均匀切分，一半是为了算力均衡，另一半正是为了这个。

顺带说清 1F1B 的真正价值：朴素的 GPipe 调度是「先做完所有前向，再做所有反向」，那样每个 stage 都要压住 GA 份激活值。1F1B 把峰值从 GA 降到 PP——它让激活值显存不再随梯度累积步数增长。这才是 1F1B 相对 GPipe 的核心改进，压气泡反而是次要的。

「非相邻 stage 不通信」的一个例外

当 embedding 与 lm_head 共享权重（tied embedding，很常见）时，这份权重同时被首 stage 和末 stage 用到，它们的梯度必须相加。此时框架会额外建一个只含首尾两个 stage 的通信域做规约——这是 PP 链上唯一一处跨越非相邻 stage 的通信。不共享权重时则完全没有。

勘误与冲突核对

对整轮讨论做前后核对后确认的修正项。按字母顺序排列。A–E 与 K、L、M 是实质性错误，其余为表述不严谨或存在歧义。K、L 由「为什么每种切分都绑定了一种通信原语」这一质疑引出；M 由核对 rank 排布机制时引出。

#原表述修正
A "EP 通常复用 DP 组的卡，或单独成维" EP 不是独立于 TP×CP×PP×DP 之外的并行维度，而是对 MoE 层重新解释已有 DP×TP 平面的一个视图。world_size 公式不变。
B "TP 是唯一切进算子内部的并行" TP 切算子的参数；CP 切算子的输入，但同样需要 attention 算子改写（分块 online softmax 累加）。需要算子级改写的是 TP 和 CP 两个。
C "一层多卡——TP / EP 的常态" EP 不该与 TP 并列。EP 的 expert 在各卡上是完整的、算子未被改写，性质上更接近 PP（沿宽度划分）；TP 才是把算子分片的那个。
D "层数除不尽 stage 数就会负载不均" 整除也不均——首 stage 背 embedding、末 stage 背 lm_head 与 loss。实践中常做非均匀切分。
E "PP 通信量最小" 是单次通信量最小。总量 = 单次 × micro-batch 数 × 边界数，并不一定小。可跨机的理由是单次通信量小 + 可 overlap。
F "SP 把 AllReduce 换成 AllGather + ReduceScatter" vs "AllReduce = ReduceScatter + AllGather" 两处顺序相反但不矛盾：前者描述一层前后两个通信算子各用什么，后者拆解单次 AllReduce 的内部实现。已在 §09 展开。
G 把算子开发层的两代工具并列表述 各家的算子开发工具通常是新旧两代并存，而非并列的两条技术路线。表述时要说明代际关系，否则读者会误以为需要在两者之间做选型。
H "优化器状态每参数约 12–16 字节" 给出构成：混合精度 Adam = fp32 master weight 4 + momentum 4 + variance 4 = 12 字节。狭义只算 momentum + variance 则为 8。区间的上下界来自口径差异，应说明口径。
I rank 换算例：32 卡 TP=4 EP=8 该例隐含 PP=DP=1。补上前提，否则 global = ep×4 + tp 的换算式不成立。
J "SP（序列并行）" 术语二义：Megatron SP（TP 的补丁，同域同大小）与 Ulysses / Ring 语义的序列并行（= CP）是两个不同维度。全文已统一，见 §00。
K 「TP → AllReduce、PP → P2P、EP → All-to-All」这类一一对应的写法（见 FIG 06 交互按钮、FIG 12 图例及 §09 各小节） 并行维度与通信原语是 N:M，不是 1:1。决定原语的是切口两侧的数学关系（部分和 / 分片待拼 / 归属待重排 / 前后依赖），不是并行的名字。§01 基数表原本写对了，正文与图未跟上，已在 §09 末补解绑小节并改写图例。
L 「All-to-All 专属于 EP」 错误。Ulysses 语义的 CP 同样以 All-to-All 为核心原语（把 seq 维切分转成 head 维切分）。且 CP 一个维度就有三种主流实现，分别用 P2P、All-to-All、AllGather——这是「维度不决定原语」最强的反证。
M EP 是「对 DP×TP 平面的重新解释」（§04 勘误 A 的说法） 在经典 EP（较早版本）下成立；采用 MoE Parallel Folding 的新版应更新为：attention 与 expert 各有一套独立的 RankGenerator 与并行 mesh，二者在同一 PP stage 上共享卡，靠 token 重排衔接。结论方向不变（EP 仍不是 world_size 的第五个乘数），但机制描述从「重新分组」变成「两套独立分解 + 中间重排」。该约束随版本变动极大（经典 EP 要求 EP = DP·TP，ETP 模式要求 EP = DP，Folding 后完全解耦），引用时必须核对版本号。详见 §11。

核对过但确认无冲突的点

  • "硬件不认识层" 与 "层在时间线上是周期性波形" —— 不矛盾。前者说的是执行抽象（卡只见 kernel 队列），后者说的是可观测表征（重复的层子图产生重复波形）。
  • "TP 每层两次 AllReduce" —— 成立。Transformer 层前向中 attention 块一次、MLP 块一次；反向同样两次。
  • "一个 MoE 层前向两次 All-to-All" —— 成立（dispatch + combine），反向同样两次。
  • "激活值显存 ≈ 层数 × 单层激活值量" —— 作为一阶近似成立，未计入重计算与 SP 带来的折减。
  • "7B 单卡 64 GB 训不动" —— 成立，静态部分即约 112 GB。

对体验治理的推论

上面这套参照系的实用价值在于：它能把用户口中同一句抱怨，拆成责任方、周期、定位路径都不同的几类。

推论 1 · "算子不支持"其实是三类问题
  1. IR 层没这个算子 —— 需求是新增算子定义，周期最长
  2. 算子在，但缺这个 dtype / format / shape 组合的 kernel —— 落到某条分支上没实现，报错常表现为"不支持的输入"
  3. kernel 在，但精度对不上或性能不达标 —— 实现质量问题

三者响应路径、责任方、交付周期完全不同，但用户侧表征几乎相同（一条报错、一次跑不通）。在问题上报入口就把这三类区分开，比事后靠工程师逐个定位要省得多。

推论 2 · OOM 与利用率低是两条独立线索

"显存 OOM" 是空间侧的问题（五项占用之和 > HBM），"卡利用率低" 通常是时间侧的问题（气泡、通信没 overlap、访存密集型算子太碎）。两者在体验上的表征完全不同，定位路径也不一样，值得当作两条独立线索来拆——而不是笼统归入"性能问题"。

推论 3 · "每层都慢"与"某一层特别慢"是不同根因

前者通常是算子实现或并行配置问题，后者往往是某个特定结构（MoE 层的 All-to-All、长序列的 attention）。层这个粒度，恰好是这两类问题能被区分开的最小单位——性能报告如果不按层聚合，这条线索就丢了。

推论 4 · 维度与原语必须解耦成两个图层

如果 viewer 把「并行维度」和「连线样式」硬绑定，就是把一个 N:M 关系编码成了 1:1——用户看到 All-to-All 连线会默认「这是 MoE」，而它同样可能是 Ulysses CP。

正确做法是两者各自成层、可任意组合：维度决定哪些卡在一个组里，原语决定组内怎么连线。解耦后反而更简单，也更能暴露真实配置——当用户选了 CP 维度而连线显示的是 All-to-All 而非 P2P 环，他立刻就知道这套跑的是 Ulysses 而不是 Ring Attention。这个信息在绑定式设计里是丢失的。

推论 5 · viewer 的两个编码决策

rank 编号显示：只标 global rank，用户看 All-to-All 连线时得自己心算映射；按当前 axis 显示域内 rank，连线语义自洽但跨 axis 切换时会让人觉得"卡的编号变了"。较稳的做法是全局号常驻、域内号随 axis 高亮——编号不变，只是当前生效的那一维被点亮。

通信连线样式：三种原语的视觉语义本不相同——P2P 该画成有方向的链，AllReduce 该画成无方向的域内闭合，All-to-All 该画成多对多且各条载荷不同的流。若用同一种连线样式，用户很容易把"同步"和"转发"混为一谈。

多 rank 时间轴：只呈现单卡时间线会诱导用户把"等待"误判为"链路慢"。把多 rank 时间轴叠在同一坐标上并标出通信算子的进入 / 退出时刻，才能让真正的慢卡浮出来。

推论 6 · 三个设计判断，来自三个连环问题

「切分都落在哪」「切分有没有顺序、顺序保留吗」「诊断时能不能不分权重体激活体」——这三问连起来，其实是在替 viewer 做三个地基级的判断：

  1. 锚点唯一：界面的基本单元就是卡。并行的一切后果都落在卡上（§07），机与集群只是卡的分组背景（用来画「谁和谁近」），计算单元与 buffer 只在下钻单个 kernel 时才需要出现。不必让五级物理层级平权地占据界面。
  2. 切分是配置，不是事件。谁拿哪块在 run 开始时一次定死、全程冻结（§07），所以切分属于静态图层——画一次、常驻；需要动画的只有执行（时间线、通信脉冲）和 MoE 路由这一处例外。「静态的归属 ＋ 动态的执行」是天然的图层划分。
  3. 诊断流合进、分出。入口用三个不分体的柄（卡坐标、容器总量、shape 除号），第二步才拆成权重体 / 激活体去开处方（§07 末）——且显存曲线的形状能自动完成这一步分拣，界面可以代替用户判断。

五根轴（ℓ、h、e、b、s）在这套界面里不需要作为概念教给用户：它们只是卡的门牌号里的几位数字（§10），界面上表现为「这张卡管哪几层、哪段序列、哪批样本、矩阵的哪一条」——用户问的从来是后面这句话。

回答两个具体问题

卡是容器吗？——是，而且不止它一个

是。卡是空间容器：装权重体分片与激活体分片，容量是显存，装满就是 OOM（§08 整节讲的就是它）。

但容器不止一种。流也是容器——它装 kernel，容量是时间。两者的区别很关键：

容器装什么容量装满会怎样
卡权重体 / 激活体的分片显存字节硬失败 —— OOM，程序崩
流kernel时间软退化 —— 排不下不会崩，只是变慢

这解释了 §14 推论 2 里那条判据的由来：OOM 与「利用率低」之所以是两条独立线索，正因为它们是两个不同容器满了。一个硬失败、一个软退化，连症状形态都不一样。

rank 是容器吗？——不是，它是地址

不是。容器有容量、装东西；rank 两样都没有。它是地址——§10 已经论证过：rank 元组唯一决定这张卡从每根轴上取走哪一片，但它本身不持有任何东西。

容易混淆是因为一种转喻：口语里说「这个 rank 上跑着什么」，实际说的是「这个 rank 所指向的那张卡上跑着什么」——用门牌号代指房子。日常无害，但一旦精确起来就必须分开，比如一张物理卡带两个 device 时（§00 表 D），「rank」和「卡」的数量就对不上了。

那什么才是装 rank 的容器？是通信域。它装的是成员（rank），但它的「容量」由配置决定而非物理限制，所以严格说它是逻辑分组而非真容器——本文把它归入结构一类。

可行性：每个对象都能具象化吗

能，但不能都画成同一种东西——这正是分五类的意义。逐类看：

类别可行性说明
结构完全可行FIG 01、03、09 都在画它。注意它不该有厚度——一旦画成实心块就会被误读成「占显存」
内容完全可行，且是最适合三维的FIG 11 容器模型把体积直接对应到字节数，这是三维图相对二维最大的优势

三维只有三根空间轴，而本文的坐标系有三组（空间 4 维 · 时间 1 维 · 粒度 1 维，§12）。轴不够用是硬约束，跟画得好不好无关。

一份自称「参照系」的东西，最该说清的是它没覆盖什么。下面分三类：本文做过的简化（可能误导，必须说明）、提到但没展开的机制、以及有意划在范围外的。

一 · 本文做过的简化

最需要说明的一处：「TP 切 h」其实合并了两根不同的轴

为了让「五根轴」这个框架成立，本文把 TP 的切分统一写成「切 h 隐藏维」。实际上 TP 在一层里切的是两个不同的东西：

  • Attention 部分按 head 切。W_Q/W_K/W_V 名义上是 [H, H]，实为 [H, num_heads × head_dim]，TP 沿 num_heads 切，每卡拿 num_heads/TP 个完整 head。
  • FFN 部分按中间维切。up 投影 [H, 4H] 按列切成 [H, 4H/TP]，down 投影 [4H, H] 按行切成 [4H/TP, H]——切的是那个 4H，不是 H。

这个合并掩盖了一个重要事实：TP 的上限来自 head 数。TP ≤ num_heads（用 GQA 时更严，受 num_kv_heads 约束），这正是 §11 里 num_attention_heads % TP == 0 那条约束的来源。把 h 当成一根连续可切的轴，会让人以为 TP 可以一直加大——实际上撞到 head 数就到顶了。

其二，全文默认均匀切分。§10 那组区间公式（ℓ ∈ [pp_rank·L/PP, …)）假设每根轴都均分。实际上 PP 常做非均匀切分（§06 勘误 D）、CP 用 zigzag 取不相邻的两段（§11）、MoE 的 expert 分配也可能不均。公式给的是骨架，不是实现。

其三，34·B·S·H 这个激活值系数有适用条件。它假设开启 SP、用 flash-attention 消掉了 [B,heads,S,S] 那两项、且不做重计算。三个条件任意一个变化，系数就不适用。文中所有显存估算都是量级估算，用于看趋势，不能拿去做容量规划。
