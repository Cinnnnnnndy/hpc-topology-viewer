逻辑魔方LogicalRubikCube

01场景说明必填

逻辑魔方把一个训练/推理作业里的每一张加速卡（rank）画成一个恒定大小的小方块： 1 小块 = 1 卡 = (TP, PP, DP) 坐标的交点，另叠一层 EP 桶身份。 整堆卡可以按不同并行轴重新堆放——这就是「形态」。切形态只换投影轴、不改变卡本身， 卡群以 0.5s 飞行动画落到新位置。

它解决的问题：大规模并行作业里「谁和谁一组」是四维关系（TP / PP / DP / EP）， 一张二维表或一张物理拓扑图只能表达其中一层；而现场真正要回答的问题是 「这批异常卡属于哪一维」「这一维的通信此刻在跟谁收发」。 逻辑魔方把维度关系变成空间形状：异常若沿某一维成组，切到对应形态就 snap 成一整块 （一面墙 / 一块板 / 一整段），根因类别当场可见。

形态一共五种，但分工不对称：PP流水 / TP切片 / EP聚簇 / DP平铺 四个各冲着一个具体问题去 （慢段 · 同槽位坏件 · 桶故障 · 慢副本），「标准」不是第五种形态，是那四种的基准投影—— 它自己不回答任何问题，留着是为了当对照系、当密排 2D 平面的归属地、当整网层联动的入口（见 3.2）。 按钮因此按 PP · TP · EP · DP · 标准 排，落地在第一个。

02场景引导必填

入局设计师用三个问题判断该不该用这个 Pattern：

  1. 对象是不是「同一批同构单元」？——rank / 卡 / 实例，成千上万个，个体没有独立形状。
  2. 它们之间是不是多维分组关系？——同一个个体同时属于 2 个及以上分组维度（TP 组、PP 段、DP 副本、EP 桶）。
  3. 用户要回答的是不是「形状问题」？——谁和谁一组、异常属于哪一维、这一维此刻在跟谁通信。

三个都为「是」→ 用逻辑魔方。任意一个为「否」→ 见下表的替代方案。

该用（Use When）

03场景设计必填

3.1 画面结构

整个 Pattern 是一块画布 + 四组浮层。浮层一律浮在画布上，不切分画布——3D 场景的取景会自动为浮层留白 （chrome:false 嵌入时由宿主接管工具栏，也不再留白）。

区块位置放什么 / 不放什么
① 名称顶栏左裸文字浮在画面上，不套卡片——叠两层底会让底色发虚
② 配置顶栏右常驻三组 segmented-control（选中态 --primary）：形态 → 视角 → 剖面，同一排、不另起一行 + 播放 + 「更多」抽屉 + 宿主控件插槽。着色 / 注入 / 连线 / 时间 / 并行一律进抽屉
③ 详情卡画布左侧选中一张卡后出现，结构见 3.8；右上角 × 取消选中
④ 图例画布右下分「着色 / 连线」两段，一行一条，只有色块 + 名字；读法与为什么不写在这里
⑤ 阶段轨道画布底部悬停弹出，可拖拽定位；播放/暂停常驻顶栏
问号气泡各控件行首写成一小段文档：kicker → 一句定义 → 选项清单 → 注意事项 → 一块带边框的「此刻」。随当前形态 / 视角 / 注入 / 选中态更新
剖面为什么排在「视角」后面而不是另起一行。视角答「从哪个方向看」，剖面答「这一屏被折掉的那一维翻到第几层」—— 后者随视角而变，是视角的下游：紧挨着才读得出这层关系。这一排只放最短的形态：开关 + 滑杆 + 一句读数（PP=0）， 「折了几张、正翻哪一层」收进它自己的问号气泡，顶栏因此不长个子（仍是一行）。3D 下没有折叠维，整组连同问号一起收起——留一个翻不动的滑杆比不留更费解。

3.2 五种形态：四个问题 + 一个基准

形态只改变卡摆在哪（谁挨着谁），不改变卡本身、也不改变颜色。 哪一维被堆成一整块，那一维的问题就现出形状。

「标准」不是第五种形态。另外四个各冲着一个问题去，它没有——留着它是因为三件具体的事，文案就直说这三件：

  1. 对照系——三根轴都不做 emph 拉开，「换形态只是换投影轴」才有个基准；
  2. 三个密排 2D 平面的归属地——别的形态把自己那根 emph 轴折进视线时，那一屏就退回成标准的同名平面（TP切片 / PP流水 的侧视因此收编掉，不重复给）；
  3. 整网层联动的入口——selectLayer() 的紫色切片只在这个坐标系里成立，所以它会主动切到标准（与 selectBucket() 切到 EP聚簇 一致）。原先只记状态不切形态：在别的形态里调用它，画面静默地什么都不发生。
轴分配的判据：这一维要不要一段段地读。标准的三根轴是 X=PP · Y=DP · Z=TP（曾是 X=TP · Y=PP · Z=DP）—— PP（第几段 · 管哪几层）与 DP（第几个副本）都要一段段读，TP 不要：标准里一整根纵深行就是一个 TP 组，组内没有歧义可分。 所以把要读的那两维摆上屏幕的横纵两轴，前 PP-DP 面因此是一张现成的「哪一段 × 哪个副本」表；TP 收进纵深，翻它用剖面。 方向也有讲究：PP 左→右 = Stage0→末（与 PP流水 同向，两个形态之间不用重新学一次），DP 上→下 = DP0→末。 PP 在这里走 spread 档（1.8×）而不是 PP流水 的 emph 档（4×）：段与段之间有看得见的空档、读得出是「四组」而不是「一片」， 但「把这根轴拉开」这个动作仍然归 PP流水——两者差一个量级，而不是差一点点。 连带两处：整网层的紫色切片变成竖着的一张板（跨 Y=DP 与 Z=TP），PP 分段的分割线与命中区切的方向从 Y 改成 X。

按钮的显示顺序 = PP · TP · EP · DP · 标准：前四个按并行维排（与设计系统 sidecar 的并行切换同一顺序，读者的肌肉记忆一致）， 标准排到末位——「先挑一个问题，实在要看全貌再回到标准」这层关系不用读文案就看得出来。 顺序用 CSS order 调，DOM 顺序与形态序号保持一致，URL 参数 / 键盘序 / 测试都不受影响。

3.3 视角、主屏与剖面

轴测 3D 可拖拽旋转；顶 / 前 / 侧是正交锁轴的 2D 投影，会把与视线平行的维折叠。 任何正交视角下拖动即从当前朝向无缝转回 3D（平移不算，见 3.7）。

形态3D顶前侧

TP切片✓DP-TP 面 ★TP-PP 面折掉 emph 轴 → 收编
EP聚簇✓桶-域 面 ★桶-PP 面域-PP 面
DP平铺✓副本网格 ★列-PP 面行-PP 面
标准✓ ★PP-TP 面PP-DP 面TP-DP 面

★ = 该形态的主屏（bestView，见下）。表头的 A-B 面 读作平面： 破折号两侧是这一屏留下的两根屏幕轴，没写出来的第三根被折进视线。 不写作 A×B——本 Pattern 里 × 是真的乘法（rank = TP×PP×DP），写在视角上会被读成数量相乘。

视角收编的判据是逐屏的，不是逐形态的。一个形态之所以不同于标准，全在它那根被拉开的 emph 轴（TP切片的墙、PP流水的段，步距 4×）： 这根轴留在屏幕上的两屏（顶 / 前），墙与墙之间是看得见的空档，「这是第几片 / 第几段」在这里才数得清 → 保留； 这根轴被折进视线的那一屏（两者都是侧视），空档随之消失，剩下的步距签名与标准的同名平面逐位相同 → 那一屏就是标准，不重复给出。 早先「与标准共享三轴 ⇒ 三平面全重合」是把这条判据用到了整个形态上，收多了——两个形态的顶 / 前两屏都是标准没有的平面。 被收编的那一屏与标准的同名平面仍是同一批格子，只差一次 90° 转（TP切片侧 = DP×PP ↔ 标准前 PP-DP；PP流水侧 = DP×TP ↔ 标准侧 TP-DP）。 已发出的 ?view=side 链接不会报错：非法视角回落到 3D。

每个形态有一个主屏「最该看的一屏」——由它要回答的问题决定，不是由好不好看决定；主屏在视角按钮里排到 3D 后面的第一个（位置本身就是推荐，DOM 顺序仍与视角序号一致）。

3.4 剖面：默认开在第 0 层

剖面只在正交 2D 出现，按最外层折叠维逐层翻。三条约束是一体的：

  • 默认开、开在第 0 层——默认关等于让人第一眼就吃一个折叠（每格 N 张卡叠着），还得先发现有这么个开关。把需要解释的那个状态放在默认，是反的。现在 2D 一进来每格就只有一张卡、所见即所得，关掉才是「把 N 张叠在一起看」。
  • 滑杆任何时候都不置灰——置灰读作「这功能不可用」，而不是「先按一下旁边那个按钮」；拖滑杆本身就是「我要逐层看」的意思，所以拖动即自动开。
  • 剖面外的卡不画（不是缩小压暗）——2D 里被折的那一维正对着视线，缩小的那一粒与剖面内那张卡在屏幕上完全重合，读出来就是每张卡正中多了个灰方块。图例里的「剖面外」一条随之撤掉：画面上已经没有这个颜色可对。聚焦压暗不这么处理——那些卡各占各的格子，缩小是读得出的对比。

「这一格叠了几张、正翻到第几层」由剖面那组的读数（PP=0）与它的问号气泡说，画面上不再常驻粒度贴士——这是本 Pattern 最后一处「解释常驻画面」的例外，已撤。

3.5 标注：落位由「标的是哪根轴」推导

一个标记标的永远是「某根世界轴上的某个位置」，那么它摆哪儿就不该由人逐处去猜。 2D 的落位规律：下方 = 横轴 · 左侧 = 纵轴 · 被折进视线 = 这一屏不出 · 场内不放标记（与二维图表一致）。 这么定死之后：① 标签之间永远不会互相压（各自占着自己那条边上的一个位置）；② 换视角、顶视转 90°、换配置，标记都自动跟到该去的边上，不需要逐处再调。

规则怎么做不这样会怎样
3D 的刻度也贴轴 三根轴各认一条棱（X 地面前沿 · Z 地面右沿 · Y 左后竖棱），整排出刻度，疏密与 2D 共用一套算法（间距按真投影量，不是世界距离除以每像素世界量） 那边整排、这边只剩一句「墙内竖=PP×5」的散文，读者得换一套读法；块标浮在半空则转个角度就飘走
两种字牌，两套尺寸规则 贴边的（轴刻度、分段牌）= 图表框架 → 固定屏幕尺寸（LABEL_PX，默认 16px）；贴几何体的（TP0 / 桶0 / 列0）= 场景标注 → 世界尺寸固定 + 屏幕像素地板兜底 混成一种：要么 3D 里的注记不跟着结构走，要么轴刻度缩远了读不出
字号只有一个入口 mount({labelPx}) / setLabelPx() / ?label=，9–28，越界回落 16 散落的字号常量会让「整体调大一点」变成逐处翻找
摆不下就少摆几枚 牌是固定屏幕尺寸 →「摆不摆得下」可算：量出占位除以相邻两项间距就是抽样步长；逐屏各算各的（同一批标记在横轴量宽、在纵轴量高），疏密交给相机实时算而不是建的时候定死 建时定死的步长偏大（明明放得下却少了几枚），缩放后更全不作数
一条边上只排一行 抽样已经保证摆得下，不再错行；3D 沿块步距自然排开已是一道斜梯，也不错行 抽样 + 错行两套办法叠上去，排成上上下下的锯齿
再补一遍跨轴检查 抽样只管一根轴自己，两根轴共用的那个角落它管不着 → 疏密算完做一次屏幕盒相交检查，冲突时留段名、丢刻度（刻度还能悬停问出来） 横轴末位与纵轴末位各自合规，投到屏幕上照样叠在一起
段标按边选形状 落到下方那条边时抽样量的是宽度，段标拆成两行（PP0 / L0-L11）宽度减半；落到左侧时量的是高度，一行更省 → 保持一行。3D 用同一个两行形状（轴测里投影会缩短，更需要窄牌） 一行 PP0 · L0-L11 要约 140px 而列距约 118px，四段被丢掉两段——那不是「密了少摆几枚」，是把主要信息摆没了
判叠优先级显式声明 跨轴冲突时留段名、丢刻度，优先级在建标记时用 rank 传进去 段标为了跟着抽样一起疏密也走了 series，「非 series 才是段名」的旧判据就失效了，变成谁先建谁赢（纯看代码顺序）
3D 里 X 与 Z 的刻度坐不同半径 两条边都贴着地面走、在近角交汇 → 外让距离分档（Z 比 X/Y 远一档），角落自然分开 同一个距离会让两串刻度在角上挤成一堆（标准 3D 里 PP3 与 TP1 只差 35px），判叠必然枪毙一枚——而 TP 一共才两枚，丢一枚就丢掉一半
抽掉的块靠悬停问出来 每一段都有一个看不见的命中盒，按分割线切满（不是只裹住卡），悬停报出与规格牌一样的两行；命中优先级 卡 > 连线 > 分段 抽样之后多数块没有牌，块却还在那儿；只裹卡的话块间空档悬停无反应

「谁和谁一组」不随视角变，「画不画得出来」随视角变

哪些 rank 是对端，是作业本身的事实——若随相机变，就成了「换个角度看，同组的人换了一批」，那是假的。 所以通信组的计算与视角无关，详情卡那四行身份也不动。随视角变的只能是画法：

  • 折叠维不画走线。正交 2D 把一根世界轴折进视线，沿那根轴排开的组全部投影到同一个像素——走线长度是 0。 实测（标准 · 选中一张卡）：前 PP-DP 面 TP=0px · 顶 PP-TP 面 DP 与 EP 都是 0px · 侧 TP-DP 面 PP=0px—— 每个 2D 视角都至少有一维如此，这不是巧合而是折叠的定义。 问题不在于画了根看不见的线，而在于画面与文案打架：图例把这一维加粗成「此刻主导维」、详情卡写着「此刻 TP 主导」，读者去画面上找那根青线找不到，合理的结论是「这个图坏了」。 现在不画，改由图例那一行压暗 + 注明「折进视线 · N 卡重合，去 3D 看」，详情卡的「此刻」下面也补一句。 这一维的通信真实存在，所以行不删、量照给，缺的只是「这一屏画不出来」这句话。
  • 判定读「这一屏留下哪两根轴」，不读相机——同一形态同一屏结论恒定，与缩放平移无关，因此不必挂进渲染循环；代价是换视角必须重建走线，否则还留着上一屏的画法。
还欠一笔：共线的两维。EP 域是 DP 组的子集，两组成员只在同一根轴上错开，于是两条线叠在同一列里——紫色整根压在蓝色底下，跨度不是 0 却一样读不出来。 试过按地铁图并行线路的老办法错开半格，实机看下来代价更大：走线唯一的锚是「端点落在卡心」，线一挪开，读者就得先在心里把它挪回它连的那两张卡上——EP 与 DP 叠着至少还各自指得准，错开之后两根都不指着谁了。 已回退，2D 与 3D 重新走同一套端点规则。真要解，方向多半是同屏只画一维（跟着「此刻主导维」走），而不是把两根都画出来再想办法分开。

3.9 着色透镜、异常注入与打光

着色是给卡上色的镜头，只改颜色不改结构：状态热力（跟着阶段走的绿→黄→红）/ 按 TP·PP·DP·EP 分组 / 按主机·Pod 分组（物理落位透镜）。注入不是另一种镜头，而是接管着色—— 一旦注入非「无」，卡色改由故障决定（受影响卡 = --danger，其余按低负载淡色）， 着色镜头暂时让位、图例同步切换，选回「无」即恢复。

色的用途取自约束
负载热力--success → --warning → --danger 三段插值与图例那条色带同源，颜色逐格一致
异常组--danger红黄绿是状态色专用，其他语义不得占用
分组着色highlight 六族的深档 600/700 与浅档 300共 12 色循环，两档交错排不取 400/500：那是色卡里彩度最高的一段，几百上千张卡铺满会糊成一片荧光。交错而非分块，是因为蓝 / 靛 / 紫三族色相只差 25~55°，同档相邻分不开——前几位先用真正拉得开的色相，再靠明度差拆开近色相。组数超过色环时图例注明「同色非同组」
维度签名色TP --dim-tp · PP --warning · DP --primary · EP --highlight-l0a-violet-400画在网格与走线上，不画在卡面
物理链路层级同机 UB ub-green · Pod 内 rail mte-amber · 跨 Pod l0b-deep-violet-600只出现在文字与悬停提示里，不画成 3D 细线或包围框
网格 / 外框 / 字牌 / 场景底--border-* / --surface-* / --backgroundThree.js 吃不了 CSS 变量 → 挂载与切主题时 readTokens() 解析成色值
打光总增益必须 ≈ 1。卡是 MeshStandardMaterial，出射色 = 材质色 ×（环境 + 平行×N·L）。 增益 > 1 会把 token 色顶到通道上限（读成荧光），并且图例色块（CSS 直接取 token）与画面对不上——图例与画面一致这件事，一半靠 readTokens()，另一半就靠这里。 现为环境 0.74 + 主光 0.32 + 背光 0.10：顶面 ≈1.0（所见即 token 色）、立面 ≈0.85、背面靠背光托住不发死，三个可见面仍差出约 15% 的明度阶梯，立体感不丢。 若哪天调亮打光，聚焦压暗的系数要跟着往下压，否则「压暗」看起来还是一片亮。

把真实体量（4000 卡）当落地配置一张卡只剩两三个像素，四种形态的差别糊成一片色块 → 落地 128 卡，真实体量留作预设
让平移也把正交视角踢回 3D在顶视里挪一下看别的区域是很自然的动作——转是转、挪是挪
靠调整 DOM 顺序改按钮的显示次序形态 / 视角的序号是 URL 参数、键盘序、测试的依据 → 显示次序用 CSS order 调
给某个单独的标记开字号小灶字号只有 LABEL_PX 一个全局入口，散落的常量会让「整体调大一点」变成逐处翻找
把固定屏幕尺寸的字牌尺寸并进取景包围盒牌的世界尺寸由相机反算，并进去会自我反馈（取景放宽 → 牌变大 → 再放宽，永不收敛）——只并锚点位置
标准把要一段段读的维藏进纵深、把无歧义的 TP 摆上屏幕轴轴分配的判据是「这一维要不要一段段地读」——PP / DP 要，TP 不要 → X=PP · Y=DP · Z=TP，前 PP-DP 面才是一张现成的表
给标准的 PP 上 emph 档（4×）那是 PP流水 的定义动作，标准跟着拉开就没有基准可对照了 → 标准用 spread（1.8×），两者差一个量级
把段标塞成一行然后指望抽样兜底下方那条边量的是宽度，一行 ~140px 而列距 ~118px，四段丢两段 = 把主要信息摆没了 → 拆两行；左侧那条边量高度，一行更省
靠「是不是 series」判断跨轴判叠的优先级段标也走 series 之后这个判据就失效了，变成谁先建谁赢 → 优先级显式传 rank，规则是段名 > 刻度
3D 里 X 与 Z 的刻度用同一个外让距离两条边贴地面走、在近角交汇，同距离会挤成一堆并被判叠裁掉 → 两根轴的标注坐在不同半径上
让走线的「谁和谁一组」随视角变那等于说换个角度看同组的人就换了一批——通信组必须视角无关，随视角变的只能是「这一屏画不画得出来」
在折叠维上照画走线成员全落在同一个像素，画出来是长度为 0 的管子，而图例还把它加粗成「此刻主导维」→ 不画，图例那行压暗并注明
拿相机去判断「这一维在这一屏塌了没有」读「这一屏留下哪两根轴」就够，结论与缩放平移无关；代价是换视角必须重建走线
把重叠的走线整条挪开来分辨走线唯一的锚是「端点落在卡心」，挪开就不指着谁了——错开半格试过已回退，宁可叠着
用黑色笼子罩住选中卡黑不在这套色卡里，笼子还盖住卡自己的着色 → 用卡同色的涟漪呼吸灯

06设计原则非必填

规则的价值在于：换任何并行数字都自动成立，新增维度（CP / SP…）或新增形态只需按同样规则声明轴的意图，不引入新的魔法数字。

原则名称描述说明应用建议
① 卡块恒定 一张卡是恒定的正方体，换形态、换配置都不改变它的大小与形状。 卡块几何与取景留白都以它为唯一事实源；需要「更好看的比例」时改的是步距，不是卡。
② 步距由规则推导 单维轴步距 = 卡块尺寸 + 缝隙(成员数) × 层级倍率。缝隙按成员数分档（多则紧、少则松），层级倍率表达意图：dense / normal / spread / emph。哪一维放哪根轴，看它要不要一段段地读——要读的摆上屏幕的横纵轴，不要读的收进纵深。 新增一根轴时只声明「成员数」和「意图」，不要写死数值；长轴不被拉成细丝，短轴不退化成薄片。
③ 复合轴分块 外维分块 + 内维紧邻：外维步距 = 内维总跨度 + 随跨度成比例的块间留白。 板 / 墙一类结构一律这样声明，任何规模下块与块都清楚分开。
④ 2D 可读性 3D 摆法必须同时对每个正交视角成立：任一视角下屏幕两轴的最细步距之比 ≤ 4；会退化成薄片的内维折成 2D。 出图前把顶 / 前 / 侧都过一遍；出现稀疏条纹就是这条被违反了。
⑤ 网格即语义 网格线一律画在格边界上（卡落在格子里、不被线穿过）；线分两级——细分格线虚线·细·中性淡，分段边界 / 块框实线·签名色·高一档不透明度；轴向不画任何裸线与箭头；选中聚焦时网格整体提亮。 方向交给刻度与文案（L0（上）→L47（下））；分段一律用块与块之间的分割线（n 块出 n−1 条），最外沿交给外框；每组线登记它躺在哪个平面，正交 2D 只画屏幕那一面。
⑥ 视角收编 · 如实折叠 判据是逐屏的：形态的 emph 轴留在屏幕上的那几屏才是它自己的，被折进视线的那一屏与标准逐位相同 → 收编。每个形态另标一个主屏，由它要回答的问题决定。 宁可少给一屏，也不要给一屏会让人读错的；折叠交给剖面（默认开在第 0 层、滑杆不置灰、剖面外的卡不画），「叠了几张」写在读数与气泡里，不常驻画面。
⑦ 色出一源 所有颜色来自设计系统 token；3D 材质在挂载与切主题时由 readTokens() 解析 token 得到色值。红黄绿是状态色专用。 图例与画面因此天然一致；缺色族（如 TP 的青）由 pattern 自备并标记「待回补上游」，不要就地造一套 HSL。
⑧ 注释纪律 落位由「标的是哪根轴」推导——2D：下方 = 横轴 · 左侧 = 纵轴 · 折进视线则不出 · 场内不放；3D：三根轴各认一条棱整排出刻度。整句解释一律进问号气泡。 牌摆不下就按屏抽样少摆几枚（抽掉的靠悬停问出来），一条边只排一行；疏密交给相机实时算，不在建的时候定死；再补一遍跨轴的屏幕盒相交检查。
⑨ 走线三层 casing（底色外套）+ 彩色线芯 + 流动暗点；方向只由点的流向表达；点的快慢对应该阶段的通信节奏。 直线折线逐段建管保证顶点精确，只有长边画成两端落在卡心的外凸弧；改完跑回归脚本。
⑩ 界面分工 常驻只留决定画面怎么摆的控件（形态 → 视角 → 剖面，同一排），筛选与工况收进抽屉；图例只列颜色与名字；详情卡按 inspector 结构给「定义 · 当前值 · 状态判断 · 执行上下文」；问号气泡写成一小段文档。 任何想常驻在画面上的解释性文字，先问一句「它能不能进问号气泡」；需要解释的状态不要放在默认（剖面默认开、滑杆不置灰），也不要用 disabled 表达「还差一步」。
⑪ 一名一物 同一根轴在画面上只有一个名字（常驻标记一律用维度名 PP0，行话 Stage 只写在悬停与横幅里）；层号一律 0 基；视角写作平面 A-B 面，× 只留给真的乘法。 牌上只留「身份 + 这个形态最要紧的那个限定」，规格收进悬停——信息分两层，而不是减少。
⑫ 落地给能读出东西的那一档 落地形态 = 四个问题导向形态中的第一个（PP流水），不是基准投影；落地配置 = 每张卡看得清的规格（128 卡），真实体量作预设一键切。 开门第一眼要能读出东西。规模大不是问题，「读不读得出」才是。
⑬ 色与光是一件事 分组色取深档 600/700 与浅档 300 交错，避开彩度最高的 400/500；打光总增益 ≈ 1（顶面所见即 token 色）。 图例色块是 CSS 直接取的 token——画面只要被增益顶亮，图例就与画面对不上；调亮打光时，压暗系数要跟着往下压。
⑭ 画不出来就说出来 「谁和谁一组」是作业的事实、不随视角变；「这一屏画不画得出来」随视角变，必须逐屏判：折叠维的走线长度是 0，不画，改由图例那一行压暗并注明「折进视线 · N 卡重合，去 3D 看」。 行不删、量照给——缺的只是那句话。画面与文案打架比少画一根线严重得多：读者找不到被加粗的那一维，只会认为图坏了。

08FAQ拓展

EP 为什么不乘进 rank 总数？

EP 折入 DP 轴、不新增轴：副本 rep 持有专家桶 rep % ep，相邻 ep 个副本构成一个 AllToAll 域。所以 rank = tp × pp × dp，ep 只要求整除 dp。落地档 2·4·16·8 = 128 rank、8 个桶、2 个 A2A 域。

为什么「标准」排在最后，落地却是 PP流水？

四个形态各回答一个具体问题，标准是它们的基准投影、自己不回答问题。开门第一眼给一个能读出东西的形态，比给一个「全都在这儿」的对照系更有用；按钮又是按 PP·TP·EP·DP·标准 排的，落地在第一个，选中态就在最左边。mount({mode}) / ?mode= 照旧覆盖。

标准的三根轴为什么是 X=PP · Y=DP · Z=TP？

判据是这一维要不要一段段地读：PP（第几段 · 管哪几层）与 DP（第几个副本）都要，TP 不要——标准里一整根纵深行就是一个 TP 组，组内没有歧义可分。把要读的那两维摆上屏幕的横纵两轴，前 PP-DP 面就是一张现成的「哪一段 × 哪个副本」表；TP 收进纵深，翻它用剖面。PP 走 spread（1.8×）而不是 PP流水 的 emph（4×）：读得出是几组，但「把这根轴拉开」仍然归 PP流水。

切到 2D 之后，某一维的走线不见了？

那一维被折进了视线：它的成员在这一屏全落在同一个像素上，走线长度是 0。画出来是一根看不见的管子，而图例还把它加粗成「此刻主导维」——画面与文案打架。所以不画，改由图例那一行压暗并注明「折进视线 · N 卡重合，去 3D 看」，详情卡的「此刻」下面也补一句。通信本身真实存在，身份与量都照给；切回 3D 就能看到。

TP切片 / PP流水 为什么只少了侧视？

收编的判据是逐屏的。这两个形态与标准的差别全在那根被拉开的 emph 轴：它留在屏幕上的两屏（顶 / 前），墙与墙之间有看得见的空档，「这是第几片 / 第几段」在这里才数得清 → 保留；它被折进视线的那一屏（侧视），空档消失、步距签名与标准的同名平面逐位相同 → 那一屏就是标准，不重复给。早先按「与标准共享三轴」把整个形态的 2D 都收掉了，收多了——PP流水 甚至换了轴分配（X=PP · Y=TP）。

为什么落地 128 卡，而不是真实的 4000 卡？

不是跑不动——布局已在 1 至 8192 卡上验证零重叠。是读不出：4000 卡时一张卡只剩两三个像素，墙 / 段 / 桶 / 板的差别糊成一片色块，第一眼读到的是一团颜色而不是一种堆法。128 卡下每张卡看得清、每一段数得出；真实体量在「并行」那排一键切过去。

2D 里的标记为什么有时少几枚？

牌是固定屏幕尺寸，所以「摆不摆得下」是可算的：量出牌在这条边上占几像素，再与相邻两项的间距一比，摆不下就按步长抽样少摆几枚——像正经的图表轴，缩放时还会自动加密 / 变疏。抽掉的那几块靠悬停问出来（命中区按分割线切满，块间空档也有反应），信息一条没少。

3D 标注太小 / 太大，怎么调？

只有一个入口：mount({labelPx}) / setLabelPx(9..28) / ?label=，默认 16px，越界回落 16。不要为某个单独的标记开小灶——散落的字号常量会让「整体调大一点」变成逐处翻找。

怎么把当前这一屏发给别人？

直接复制地址栏：URL 即状态（形态 / 视角 / 并行度 / 着色 / 注入 / 阶段 / 选中 rank / 主题 / 字号，见 5.1）。发布时每个资源链接都会打上 ?v=<短 SHA>，pattern.json 里写入同一个 version，对方能核对自己拿到的是哪一版。

能不能改配色 / 换成业务自己的品牌色？

可以，但只能在页面级覆盖设计系统 token——pattern 只消费语义 token，3D 材质也经 readTokens() 读同一批 token，所以覆盖后画面与图例会一起变。禁止在宿主 CSS 里覆盖 .prc-* 的具体色值，也不要调打光增益（见 3.9）。

只想嵌一块画布、工具栏用我自己的，怎么做？

mount(el, { chrome: false })：pattern 不再渲染自带工具栏，取景也不为面板留白，全部控制走 handle 上的 setMode / setView / setSlice / setColorBy … 一组 API。

要新增一个并行维度（CP / SP）怎么办？

不要新写一套坐标计算。在 pattern.js 的 SP / modes 里按原则 ①–⑥ 声明这根轴的意图（放哪根轴、用什么层级倍率、正交视角折叠哪些维、主屏是哪一屏），布局会自动推导出来；同时补上该维的签名色与图例条目、以及这个形态的 canonical 分段。
