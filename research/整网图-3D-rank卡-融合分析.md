> 难点是**整网对象的并行切分** —— 核心是**把算子装进对应的 rank 里**；有 CP/SP 时还涉及

## 0. 三句话

1. **rank 卡内部不是整网图的裁剪，是整网图的「并行化展开」**（lowering）：节点集合既有减
   （别的 stage 的层根本不存在）也有加（HCCL 算子是并行化产生的，逻辑图里没有）。
   通信算子正是这个差集 —— 这是「输入输出 × attention/MoE × HCCL」三者关系的正面答案。
2. **什么该进 3D 空间、什么该进卡内部，不用拍脑袋 —— 图的数据里已经写死了**：
   整网图里 `repeat: true` 的 cluster 就是一根被折叠起来的并行轴（decoder-stack→PP，
   moe-block→EP），3D 有空闲的轴可以把它展开；`repeat: false` 的地方切分发生在**张量内部**
   （TP/CP/SP 切的是 head/ctx/seq），那只能画在卡的内部。
3. **「六个面各管一维」是助记不是坐标**（一个立方体只有 3 根轴）。真正的三维体系应该按
   **轴的性质**分三类：图轴（PP）→ 空间；张量轴（TP/CP/SP/EP）→ 卡内切分；数据轴（DP）→ 复制壳。
   现有实现其实已经站在这条线上了（`nest` 壳 + 卡上切分 + PP 形态），只是没被命名。

## 1. 地基：三类轴，性质根本不同

资料把 DP/PP/TP/EP/CP/SP 并列成「六维」，这在**讲切分对象**时是对的，但在**做三维布局**时会
误导——因为这六个东西切的根本不是同一种坐标：

| 类别 | 维 | 切的是什么 | 在整网图上表现为 | 该用什么表达 |
|---|---|---|---|---|
| **图轴** | PP | 计算图的**节点集合**（层序） | cluster `decoder-stack` 的 `repeat` 次数 | 3D 的一根**空间轴** |
| **图轴（半）** | EP | 计算图里**被复制的分支**（专家） | cluster `moe-block` 的 `repeat` 次数 | 3D 空间轴 或 卡内桶 |
| **张量轴** | TP | 权重张量的 head/hidden/ffn/vocab 轴 | 节点**不变**，shape 变小 | **卡内切分**（方块再切） |
| **张量轴** | CP | 激活张量的 ctx 轴 | 节点不变，shape 变小 | 卡内切分 |
| **张量轴** | SP | 激活张量的 seq 轴 | 节点不变，shape 变小 | 卡内切分 |
| **数据轴** | DP | 数据 batch（整图复制） | 图**完全不变** | **复制壳**（嵌套容器） |

一句话判据：**PP/EP 改变「有哪些节点」，TP/CP/SP 改变「节点里张量多大」，DP 什么都不改。**

这条判据直接决定了显示形式：
- 改变节点集合的维 → 在 3D 里**摆开**（不同位置放不同的子图，位置有真实含义）；
- 改变张量大小的维 → 在 3D 里**摆不开**（每张卡的节点长得一样，摆开只是重复），必须**钻进卡里**看；
- 什么都不改的维 → 画成**壳**（外面套一层，说明"这一整坨还有 D 份"）。

> 与既有结论对齐：`public/vendor/rubik-cube/README.md` 的「六面助记」已经判定
> 「前 PP / 背 TP 摆成对面是假坐标」。本节给出的是**为什么假**以及**替代方案**：
> 不是六个面，是三类轴各有一种表达。

## 2. 分工线是从数据里读出来的，不是设计出来的

`src/vendor/model-graphviz/openpangu-graph.json`：55 节点 / 61 边 / 5 cluster，
**且每个节点自带 `x/y/width/height`（预定位）**。cluster 结构：

```
model-core (Causal LM)                    repeat=false   8 节点
└─ decoder-stack (Decoder Layer Template) repeat=TRUE   10 节点   ← 折叠了 L 层
   ├─ attention-block (Sparse MLA)        repeat=false  19 节点
   └─ ffn-block (Dense + MoE FFN)         repeat=false   7 节点
      └─ moe-block (MoE FFN)              repeat=TRUE   11 节点   ← 折叠了 E 个专家
```

两处 `repeat: true`，**恰好就是两根「改变节点集合」的并行轴**：

| cluster | repeat 的是 | 展开后的份数 | 对应并行维 |
|---|---|---|---|
| `decoder-stack` | decoder layer | L 层 → 分给 PP 个 stage | **PP** |
| `moe-block` | expert | E 个专家 → 分给 EP 个桶 | **EP** |

**这就是分工线**：2D 整网图为了可读，把这两根轴折叠成了「模板 ×N」的写法；
3D 恰好有富余的空间轴，**3D 的职责就是把这两根折叠轴展开**，
其余四维（TP/CP/SP + DP）在 2D 图上原本就无法表达（它们不改节点），交给**卡内切分**与**复制壳**。

这条判定同时解释了一个此前含糊的问题：「整网图要不要整个塞进 3D？」——**不要**。
2D 图已经把层内结构讲清楚了，把 55 个节点搬进 3D 只是把可读的东西变得不可读。
3D 只该拿走它**画不了**的那部分：层的展开、副本的复制、张量内的切分。

## 3. 整网图里已经有 6 个 HCCL 节点 —— 缺的两个正是接缝

图里这 6 个是一等节点（`kind: 'op'`），不是标注：

| 节点 | 原语 | 组 | 分片状态转换（`SHARD` 已标 `from`/`to`） |
|---|---|---|---|
| `attention_all_gather` | AllGather | TP | `seq:sp` → `seq:完整`（进 TP 区） |
| `attention_reduce_scatter` | ReduceScatter | TP | `hidden:partial` → `seq:sp`（出 TP 区，一步顶 AllReduce+Scatter） |
| `ffn_all_gather` | AllGather | TP | `seq:sp` → `seq:完整` |
| `ffn_reduce_scatter` | ReduceScatter | TP | `hidden:partial` → `seq:sp` |
| `moe_all_to_all_dispatch` | AllToAll | EP | `seq:local` → `expert:ep`（按 token 分 → 按专家分） |
| `moe_all_to_all_combine` | AllToAll | EP | `expert:ep` → `seq:local` |

**缺的恰恰是两个：`PP 的 P2P Send/Recv` 和 `DP 的梯度 AllReduce`。**
不是漏画 —— 是因为它们发生在**被折叠掉的那两根轴上**：P2P 跨的是 layer repeat 的边界，
DP AllReduce 跨的是 replica。图折叠了这两根轴，所以画不出这两个算子。

> **这就是 3D 与整网图的接缝，也是「嵌套」的真正来源**：
> 3D 展开 layer 轴 → `P2P` 才有地方画（stage 与 stage 之间的那条线）；
> 3D 复制 replica 壳 → `DP AllReduce` 才有地方画（壳与壳之间的那条线）。
> 层内的 6 个 HCCL 算子留在 2D 图里，跨层/跨副本的 2 个只能在 3D 里 —— 两屏合起来才是完整的 8 个。

## 4. 数据模型：四类实体（回答研究笔记 §5-①）

```ts
// ① 逻辑算子节点 —— 与并行无关，55 个，就是 openpangu-graph.json
LogicalOp  { id, label, kind:'op'|'tensor'|'module', parent:clusterId, colorKey, x,y,w,h }
Edge       { source, target, dashed }              // dashed = 权重/参数边

// ② 切分规格 —— 并行配置的函数，一张表（今天是 net-sharding 的 SHARD）
ShardSpec  { opId, by:[{dim,axis}], kind?:'param', partial?:bool,
             prim?, group?, from?, to?,            // 通信节点专用
             carry?:(coord)=>bool }                // 该 rank 是否持有（如 embedding 只在 pp=0）

// ③ 算子实例 —— 「装进 rank」的那个东西 = ① × rank 坐标，经 carry 过滤
OpInstance { opId, coord:{dp,pp,tp,cp,ep}, shards:[{dim,axis,idx,of,range}], shape }

// ④ 通信算子 —— 不属于单个 rank，属于一个坐标切面
CommOp     { id, prim, group:{dim, fixed:coord去掉该维}, on:edgeId,
             from:ShardState, to:ShardState }
```

四点建模要害：

1. **`OpInstance` 的键是 `(opId, coord)`，不是 `(opId, rank)`** —— 用六维坐标而不是线性 rank 号，
   因为「同一个 TP 组」= 固定其余坐标只让 tp 变，用坐标做投影是 O(1)，用 rank 号要反解。
   （rank ↔ coord 的换算口径已经统一：`rank = ((dp·PP+pp)·CP+cp)·TP+tp`，CP=1 时与
   `src/scene/data.ts` 的 `parallelMap` 逐位相同。）
2. **`CommOp.on = edgeId`** —— 通信挂在**边**上，不是挂在节点旁边。这是「HCCL 算子 = 分片状态
   的转换器」这句话的数据结构版本：边的两端状态不同 → 边上必然坐着一个原语。
3. **`carry` 是谓词不是布尔值** —— `embedding` 只在 `pp==0`、`lm_head` 只在 `pp==PP-1`、
   `routed_expert_bank` 每个 EP 桶不同。carry 决定了**不同 rank 的子图结构不同**，
   这是「PP 首末段的卡长得不一样」能被看见的根源。
4. **`shards` 是数组不是单值** —— `attention_core` 同时被 TP(head) 和 CP(ctx) 切，
   它持有的是**二维网格里的一格**（总份数 TP×CP）。只报主导维等于把话说了一半。

## 5. 通信原语可以推导，不必逐个手写

现状 `SHARD` 是给每个通信节点手写 `from`/`to`。更强的做法：**给每个非通信节点标注它的
「分片状态」，然后比较每条边两端的状态 —— 不一致就必须插一个原语，且插哪个是唯一确定的**。

分片状态 = 每根张量轴当前的处置：`{seq: 'sp'|'cp'|null, hidden: 'tp'|'partial'|null, expert: 'ep'|null}`

| from → to | 必须插入 | 组 | 出现处 |
|---|---|---|---|
| `seq:sp` → `seq:null`（收齐序列） | **AllGather** | TP(=SP) | 进 TP 区（attention/FFN 入口） |
| `hidden:partial` → `seq:sp` | **ReduceScatter** | TP | 出 TP 区（行切算子之后） |
| `hidden:partial` → `hidden:null` | **AllReduce** | TP | 不用 SP 时的行切出口 |
| `ctx:cp` → `ctx:null`（收齐 KV） | **AllGather** | CP | attention_core 之前 |
| `seq:local` → `expert:ep` | **AllToAll** | EP | MoE dispatch |
| `expert:ep` → `seq:local` | **AllToAll** | EP | MoE combine |
| `layer:k` → `layer:k+1` 且跨 stage | **P2P Send/Recv** | PP | stage 边界 |
| 反向梯度 `dp` 副本间 | **AllReduce** | DP | step 末尾 |

价值有三：
- **换并行配置时通信自动重算**（关掉 SP → 两个 AllGather/ReduceScatter 变成一个 AllReduce，
  这正是「SP 省显存的代价」的可视化）；
- **换模型不用重写通信标注**，只要标注算子的行切/列切/norm 属性；
- **「行切的输出是 partial sum」这件事从注释变成状态**，画面上可以直接把 partial 状态染成警示色 ——
  partial 是唯一一个「看起来算完了其实不能用」的状态，值得单独有颜色。

> 现有 `flowOf()` 手写了一条 decoder layer 的流水（16 步），是这张表的**实例**。
> 表化之后 `flowOf()` 应该是**推出来的**，而不是写出来的。

## 6. 落点 A：3D 场景里怎么用整网图（三种耦合，按「位置是否说谎」排序）

### A1 · 整网图当透镜选择器（已实现，需换底）✅

点 2D 图上任一算子 → 魔方按该算子的切分维重着色，每张卡显示自己持有的第几片。
**现状是拿 15 个手写抽象对象（`NET_OBJ`）当选择器，不是真图的 55 个节点。**
换底之后，「点 `q_b_proj` 和点 `kv_b_proj` 得到不同的 head 片」这种真实差别才出得来。

### A2 · 沿 PP 轴把折叠的 layer 展开（**唯一位置不说谎的空间嵌入**）★

整网图的 layout 是**竖直长条 1973×3761**，y 轴天然就是层序 —— 而 PP 切的正是层序。
所以把 2D 图的 y 轴映射到 3D 的 PP 轴是 **1:1 的、无需重排的**：

```
       stage 0        stage 1        stage 2        stage 3        stage 4
      ┌────────┐     ┌────────┐     ┌────────┐     ┌────────┐     ┌────────┐
      │ embed  │     │        │     │        │     │        │     │        │
      │ L0..L5 │─P2P→│ L6..11 │─P2P→│ L12..17│─P2P→│ L18..23│─P2P→│ L24..L │
      │        │     │        │     │        │     │        │     │ norm   │
      └────────┘     └────────┘     └────────┘     └────────┘     │ lm_head│
        ↑ 图上这一段子图悬浮在该 stage 的卡阵上方                    └────────┘
```

要点：**首末两段的子图结构真的不同**（`embedding`/`lm_head` 只落在首/末段），
所以这不是同一张图摆 5 遍 —— 它是「PP 切了什么」的直接证据。
`P2P` 算子此时终于有地方画：就是 stage 与 stage 之间那条线。

### A3 · 通信算子作为坐标切面（已实现域轮廓/通信线，需挂到边上）

通信组 = 固定其余坐标、只让一个维变化的**切面**。现有「域轮廓 / 通信线」画的是切面本身；
缺的一步是**把它和整网图的边关联起来** —— 悬停 2D 图上的 `moe_all_to_all_dispatch`，
3D 里高亮的应该是「本卡所在的那个 EP 切面」，且旁边写清 `HcclAlltoAllV`。

### A4 · 不要做的事 ✗

- 把 55 个节点搬进 3D 当立体流程图 —— 2D 已经更好，3D 只会更糊；
- 用六个面各绑一维 —— 假坐标（§1）；
- 递归几何嵌套（cube-in-cube-in-cube）到底 —— 与「4000 rank 平铺一层」是两套渲染，
  宏观→微观的**效果**用形态切换 + 相机过渡就能达成（导览已验证）。

## 7. 落点 B：rank 卡内部 = 共享布局的差分子图

这是本文最核心的显示形式建议。

**卡内该显示的东西是「本 rank 的执行子图」**，它由整网图经三步变换得到：

```
整网图（逻辑，55 节点）
  ①  按 carry 过滤       →  删掉本 stage 没有的节点（首末段的 embedding/lm_head、别的层）
  ②  按 shard 换 shape   →  每个保留节点换成它的实例：[b, s/CP, h/TP] 这样的具体形状
  ③  在状态突变的边上插入 →  加进 HCCL 节点（§5 的推导规则）
= rank 执行子图（节点数既减也增）
```

**显示形式：共享布局 + 差分着色（small multiples）。**
整网图是**预定位**的（每个节点带 x/y），这一点是白送的礼物：可以把同一套坐标当**底图模板**，
每张 rank 卡渲染一份差分：

```
   rank 0 (pp0·tp0·ep0)      rank 7 (pp0·tp7·ep0)      rank 800 (pp1·tp0·ep1)
  ┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
  │ ▣ embedding v0/8│       │ ▣ embedding v7/8│       │ ░ （本段没有）   │
  │ ▣ q_b_proj h0-7 │       │ ▣ q_b_proj h56-63│      │ ▣ q_b_proj h0-7 │
  │ ▣ attn  h0-7×c0 │       │ ▣ attn h56-63×c0│       │ ▣ attn  h0-7×c0 │
  │ ◈ AllGather TP  │       │ ◈ AllGather TP  │       │ ◈ AllGather TP  │
  │ ▣ experts E0-31 │       │ ▣ experts E0-31 │       │ ▣ experts E32-63│  ← EP 桶不同
  │ ░ lm_head       │       │ ░ lm_head       │       │ ░ lm_head       │
  └─────────────────┘       └─────────────────┘       └─────────────────┘
     ▣ 持有  ░ 不持有  ◈ 通信算子（并行化插入的，逻辑图里没有）
```

**因为位置对齐，差异一眼可见** —— 这是并排小图（small multiples）唯一的要求，也正好是这份
预定位图能白送的能力。三张卡放在一起，读者不需要读文字就能得到三个结论：
同 TP 组的卡**结构相同、区间不同**；跨 PP 段的卡**结构不同**；跨 EP 桶的卡**专家桶不同**。

配套两件事：
- **节点点开 = 张量方块**：显示该张量被哪几根轴各切几份、本卡是哪一格（`attn_core` 的 TP×CP
  二维网格已有实现，推广到所有节点）；
- **卡的边界要画出来**：卡内子图的**入口和出口都是 HCCL 算子**，这件事本身就是「一张卡不能
  单独跑完一层」的证据，比任何文字说明都直接。

> 与现有实现的关系：`装载清单`（侧栏文字）+ `装载板`（3D 摊开）+ `卡上切分`（方块再切）
> 已经把「持有什么」讲清楚了，但**丢掉了拓扑** —— 它们是清单，不是图。
> 卡内差分子图补的正是拓扑：谁接谁、通信卡在哪两步之间。

## 8. 落点 C：「场景」的可操作定义

用户说的「这些 p 的场景」，落到数据上是：

```
场景 = 并行度组合 (TP,CP,SP,PP,EP,DP) + 模型规格 (layers,heads,experts,seq,vocab,ffn)
     → 一张 55 × N 的持有矩阵 M[opId][coord] = OpInstance | null
```

有了这张矩阵，三种读法各回答一个问题：

| 读法 | 沿哪个方向切矩阵 | 回答 |
|---|---|---|
| **切分矩阵**（整网图着色） | 固定 coord，扫 opId | 这张卡装了什么（= rank 卡内部，§7） |
| **rank 装载**（魔方着色） | 固定 opId，扫 coord | 这个算子被切成几片、散在哪些卡上（= 3D 透镜，§6-A1） |
| **通信流水**（时间轴） | 沿边扫状态变化 | 一层走一遍，张量在什么时候变成什么状态（= §5） |

**场景对比**是这个模型白送的能力：两组配置 → 两张矩阵 → 差分。
「EP2 折进 DP 还是独立成维」「开不开 SP」「CP2 之后 attention 多了哪一步」——
这些今天只能靠读文字理解的取舍，在矩阵差分下是可以直接画出来的。

## 9. 与现有两个 pattern 的差距（合并路径）

仓库里已经有两套东西，各做对了一半：

| | `rubik-cube`（3D） | `net-sharding`（2D） |
|---|---|---|
| 坐标系 | 并行超立方（卡是主体） | 模型计算图（算子是主体） |
| 整网对象 | **15 个手写抽象对象** `NET_OBJ` | **55 个真图节点** `SHARD`（与图 1:1，已核对无缺无多） |
| 切分标注 | `{维, 轴, 份数, 本卡区间}` + 多维 `objShards` | `{维, 轴}` + 通信节点的 `from/to` 状态 |
| 通信 | 6 个通信带对象，绑定组 | 6 个真图通信节点 + 手写 16 步流水 |
| 拓扑（谁接谁） | ✗ 无 | ✅ 真图的 61 条边 |
| 卡内部 | ✅ 装载清单/装载板/卡上切分/细节视窗 | 侧栏装载卡 |
| 嵌套/展开 | ✅ 壳 + 形态 + 导览 | ✗ |

**差距只有一处，但它是关键的一处：3D 那边用的是手写的 15 个对象，不是真图。**
于是 3D 里读到的「整网」和 2D 里看到的整网**不是同一张图**，两屏对不上号。

合并方向（一句话）：**让 `SHARD`（55 节点，与真图 1:1）成为唯一的切分事实源，
`NET_OBJ` 退化成它的「导读分组」**（15 个带 `band`/`best 形态`/长说明的展示分组，
每组指向若干真节点 id）。这样：
- 3D 的透镜/装载/卡上切分全部改走真节点 id → 两屏天然对得上；
- 现有 15 个对象的教学价值（`band` 分组、推荐形态、长注释）不丢，只是降级为视图层；
- `graph-meta.ts` 的 `NODE_DIM`（启发式 `deriveDim`，无 CP/SP）也一并回补为 `SHARD` 的投影。

## 11. 诚实标注的缺口（不假装完整）

- **切分规格仍是静态标注**，不是从 MindSpeed/Megatron 的并行配置与 `ranktable` 解析出来的。
  换一个模型要重写 `SHARD`。数据驱动的接入口是 `src/scene/ingest.ts` 的 `JobConfig`。
- **EP 的 token 负载不均没有表达**。AllToAll 的真实代价取决于路由后每个专家收到多少 token，
  目前只画「按专家切成几份」这个结构事实。热专家拖慢整域这件事，画不出来。
- **CP 的因果掩码语义没展开**。因果注意力下 CP 各 rank 的计算量本就不均（后面的 chunk 要看
  前面全部），这里只表达上下文被切成段。
- **反向图完全没有**。`from/to` 状态表只覆盖前向；反向的通信（梯度 AllReduce、
  RS/AG 的对偶）是另一半，ZeRO 的 param/grad/optim 各自不同分片更是第三层。
- **一个算子只用主导维着色**（多维切的完整信息在卡内给全）。这是有意的取舍，不是遗漏。
