一句话结论 这 4 页材料把 Ascend 950 超节点从"终态规模数字"变成了"积木怎么拼出来的"：标卡(4卡)/Server(8NPU+2CPU)/POD(64NPU+16CPU) 三级硬件构建块，靠单层或两层 SW 的 Fullmesh+Clos 拼出 128 卡 → 1024 卡 → 1024P 集群，并且从头到尾贯穿"多个独立平面、平面间无互联"的容错设计——这些都是本仓库现有可视化数据规格（ascend-superpod-viz-spec.json）里完全没有的中间层信息。

全局位置

本仓库已有一份「昇腾超节点·各级互联」设计简报，讲的是 UB/灵衢总线如何用统一内存语义抹掉"服务器内总线"与"服务器外网络"的边界（Die→NPU→节点→机柜→超节点→跨超节点七层抽象，见 research/昇腾超节点-各级互联设计简报.md §3.1-3.2）。那份简报的数据主要来自 A3(910C/384卡) 世代，对 A5(950) 只给了终态数字（8192 卡 / 128 计算+32 互联=160 柜），没有说清 950 这台"万卡计算机"是怎么一级级拼出来的。

本篇笔记只回答这一个缺口：950 世代的硬件构建块长什么样、怎么组网到 128/1024/1024P 规模。不重复讲既有简报已经覆盖的并行流量映射（TP/EP/PP/DP 落在哪一级互联）、也不涉及可视化设计本身的交互规格——那些留在姊妹篇里。

知识地图：按什么顺序读

先懂 UB 互联的三条设计原则，才能看懂"为什么标卡/Server/POD 能像积木一样互相嵌套复用同一套协议"；懂了硬件形态，才能懂两条组网路径（Server 逐级 SW / POD 间多平面 Clos）为什么殊途同归都收敛到"1024"这个规模节点。

用语约定

本篇涉及的几个词，和本仓库既有资料（A3 世代）里的同名概念口径不完全一样，先对齐：

本篇用语指什么（950 世代）与既有资料（A3 世代）的区别
标卡x86 底座 + 4 张 NPU 卡，卡间 UB fullmesh，是最小的独立可部署 UB 互联单元既有资料的 abstraction_layers/entities 里完全没有这一级，是本篇新识别的构建块
Server8 NPU + 2 CPU，Server 内 fullmesh、出 Server 走 Clos既有 JSON 的 compute_node 是「1 CPU + 8 NPU + 1 L1 交换芯片」——950 的 CPU 数翻倍，且不含独立 L1 交换芯片这一描述
POD64 NPU + 16 CPU，1D fullmesh + Clos，是可整框部署的中等规模构建块既有资料里的"机柜 Rack"是容器概念（装节点），POD 是更接近"可整体出货的互联单元"这一新颗粒度
超节点 / SuperPOD由 POD 或 Server 组网而成的对等全互联域（128 卡、1024 卡…）与既有资料的 SuperPoD 概念一致，只是本篇给出了内部怎么拼出来
平面 (plane)一套独立的 SW 组网，多个平面并存但互不连接既有资料的 A3 UB-Mesh 描述里没有"多平面"这个说法，是 950 材料新强调的设计原则
L1 SW / L2 SW灵衢交换的两个层级，二者构成 Clos 互联与既有资料的 l1_switch/l2_switch 概念一致，可直接复用
DPU独立于 CPU 的部件，经 PCIe 接 CPU、经 UB 直接入 L1 灵衢 Switch，RoCE 从 DPU 侧出既有 JSON 用的是「擎天 NIC(VPC)」描述南北向网卡，且假设 RDMA 端口在 NPU 上（npu_rdma_port）——两者挂载点不一致，见下方「常见误解」

常见误解

✗ 错误直觉Ascend 950 的计算节点还是 A3 那样"1 个 CPU 配 8 个 NPU"。
✓ 正确机制950 的 Server 形态是 2 CPU + 8 NPU，CPU 配比比 A3 世代翻了一倍；而且 950 不再只有"节点"一级，而是标卡(4卡)/Server(8卡)/POD(64卡) 三级并列的构建块，具体用哪一级取决于目标部署规模。 ✅ 已核实-原文 CANN NEXT 直播截图·Ascend 950硬件形态：POD&Server&标卡
✗ 错误直觉RDMA/RoCE 的收发端口在 NPU 上（沿用本仓库既有 ascend-superpod-viz-spec.json 里 npu_rdma_port 的假设）。
✓ 正确机制950 的拓扑图明确把 RoCE 画在 DPU 一侧：DPU 通过 PCIe 接 CPU、通过 UB 直接入 L1 灵衢 Switch，RoCE 从 DPU 往外接；NPU 本身只出现在 UB 平面里，图上没有单独画 NPU 直连 RDMA 的线。 ✅ 已核实-原文 CANN NEXT 直播截图·UB互联特征拓扑图 ⚠️ 单一来源——只有这一张截图作为依据，与既有 JSON 的出入点尚未找到第三份材料交叉验证，标注在「待深化」里。

三种硬件形态：标卡 / Server / POD

三者是同一套 UB 协议在不同密度下的复用：都用 X4 UB 口做 fullmesh，区别只是卡数、CPU 配比、以及"出向"用什么拓扑对接更大规模。 ✅ 已核实-原文 CANN NEXT 直播截图·Ascend 950硬件形态：POD&Server&标卡

形态规模内部拓扑出向拓扑备注
标卡x86 底座 + 4 卡每卡 3×X4 UB 口 fullmesh可插第三方网卡做参数面互联本仓库既有资料里没有的最小构建块
Server8 NPU + 2 CPUServer 内 fullmesh，7×X4 UB 口出 Server 走 Clos，8×X4 UB 口CPU 配比比 A3 世代（1:8）翻倍
POD64 NPU + 16 CPU1D fullmesh + Clos；计算板每 D 出 7×X4 UB 口 fullmesh，另出 8 口接 L1 SW交换板可配成每 D 出 4 口或 8 口，分别用于框内板间 / 框间互联可整框部署的中等规模构建块

UB 互联三原则与 950 超节点拓扑

950 超节点用 POD & Server 作为基本互联单位，通过灵衢互联构建高性能集群，三条设计原则： ✅ 已核实-原文 CANN NEXT 直播截图·UB互联特征

  1. 对等架构：CPU、NPU、存储等异构组件无主从直接通信，组件对等协同——打破以 CPU 为中心的传统互联模式。
  2. 协议归一：超节点内所有节点用同一套 UB 协议互连，无协议转换网关。
  3. 全域内存语义：原生支持内存语义，兼顾异步访问的消息语义，既保证极致性能又兼顾兼容性；用内存地址访问降低编程复杂度。

这与既有简报「灵衢用统一内存语义总线抹掉服务器内外边界」的核心叙事完全一致（research/昇腾超节点-各级互联设计简报.md 第 0 节），可以互相印证，不是新论断。

组网配方：128 卡 / 1024 卡 / 1024P

材料给出两条独立的组网路径，殊途同归都落在"1024"这个规模节点上。

路径 A：Server 逐级 SW（单层→两层）

  1. 128 卡超节点：16 台 Server，单层 SW 设备，128 张卡对等全互联。
  2. 1024 卡（1K）超节点：L1 SW 先做 Server 内 8 卡接入，L2 SW 做 TOR 互联汇聚（两层）。
  3. 两档都强调"多个独立平面，平面间无互联"。
✅ 已核实-原文 CANN NEXT 直播截图·Ascend 950 server使用单层或者两层SW构建多种规格超节点

路径 B：POD 间多平面 Clos

  1. POD 可用出框单层 SW 构建 SuperPOD 超节点。
  2. L1 SW 和 L2 SW 构成 Clos 互联。
  3. 同样强调"多个独立平面，平面间无互联"；图上标注 8 个独立平面，每平面 4×SW2，向下接两组各 8+8 颗 SW1 的 POD 群，总计 128 × 8 = 1024P。
✅ 已核实-原文 CANN NEXT 直播截图·Ascend 950 POD间使用单层SW组网构建1024P超节点集群（"128*8=1024P"为图上原始标注）

成本-收益：多个独立平面，平面间无互联

机制代价收益净效果
多平面隔离（无跨平面互联） 单张卡若挂在某一平面，无法直接访问其它平面的资源；软件/调度层需要感知多平面拓扑做流量分片与容灾路由 故障域隔离——一个平面故障不拖累其它 7 个平面；线性扩展带宽——加平面即加总带宽，不增加单平面内部复杂度；每平面可独立升级/维护 大规模 RDMA fabric 的标准做法，总是值得；代价集中在软件层（拓扑感知调度），不在硬件层

手算示例：两条组网路径是否真的收敛到 1024

路径 A（Server 逐级 SW，slide 3 原文数字）： 128 卡超节点 = 16 台 Server × 8 NPU/Server = 128 ✓（图文直接给出） 1024 卡超节点 = 128 台 Server × 8 NPU/Server = 1024 ✓（图文直接给出） 路径 B（POD 间多平面 Clos，slide 4 原文标注）： 1024P = 128 × 8（平面数）= 1024 ✓（图上原始标注，direct 已核实） 若按"每份128 = 2 个 64-NPU POD"回推：64 × 2 = 128 🔸推断，未在文字中直接确认 交叉观察： 两条路径都在"128"这个中间节点上重合——路径 A 的"128 卡超节点"本身就是一个完整命名规格， 路径 B 的"128"份额也复用了同一个数字。不能排除二者说的是同一个 128-卡积木， 只是分别用 Server 单层 SW 和 POD 多平面两种方式描述其内部/外部构成；也可能是两种独立的 参考设计。文字材料未明说，已列入「待深化」。

例外与边界

  • POD 间 1024P 组网图里画了两个"128"构成框（各配 8+8 颗 SW1），但文字没有说明为什么画两份——可能代表两条独立上联路径，也可能只是版面对称的示意画法，本篇按 🔸推断处理，不作为确定结论。
  • "标卡可接第三方网卡做参数面互联"，据此推断其目标场景偏边缘/小规模推理一体机，但材料未直接给出官方命名或应用场景标签——这是推断，非原文直述。
  • DPU 的数量、端口带宽、与 CPU/NPU 的确切配比，材料未标注具体数字，只能确定其拓扑位置（PCIe 接 CPU、UB 接 L1、RoCE 对外）。
  • 本篇材料止步于 1024P，既有 JSON 给出的 950 终态规模是 8192 卡——从 1024P 到 8192 卡之间还有一段组网路径，本篇未覆盖。
